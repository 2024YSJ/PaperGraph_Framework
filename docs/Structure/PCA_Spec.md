# PCA 스펙

담당: 다예 (3순위)
관련 클래스: `src/visualize/PCA.ts`, 테스트 UI는 `src/adapter/VisualizationView.ts`

---

## 1. 무엇을 하는가

논문마다 붙어 있는 **임베딩 벡터**(현재 모델 기준 768차원)를 받아, 그래프에 찍을 **평면 좌표 (x, y)** 로 바꾼다. x·y는 PCA로 얻은 제1·제2 주성분이고, 내용이 비슷한 논문끼리 가까이 모인다.

**출력은 모든 렌더러가 공통으로 필요로 하는 최소 정보만 담는다** — 좌표 (x, y)와 원본 `paper` 참조. 시각화 렌더러도, PCA 계산 방식도 갈아끼울 수 있어야 하므로, 특정 렌더러의 선택(예: z축을 시간으로 쓰는 것)은 계약에 넣지 않는다. 시간축이 필요한 렌더러는 함께 넘어가는 `paper.publicationDate`에서 직접 계산한다 — 그때의 함정은 8절 4번에 정리해뒀다.

> **차원 수를 코드에 하드코딩하지 않는다.** 768은 지금 쓰는 모델의 값일 뿐이고, 코드는 차원 수를 데이터에서 읽는다. 임베딩 모델이 바뀌어 차원이 달라져도 코드는 그대로 동작해야 한다.

## 2. 입력

`VisualizationFlow.run()`이 `File`로 읽어온 `Paper[]`를 넘겨준다. UI의 "최근 N년으로 그래프 제한" 설정이 생기면 넘어오는 리스트가 이미 연도로 걸러져 있을 수 있는데, PCA는 받은 리스트만 처리하므로 동작에는 영향이 없다.

다만 basis(9절)와 엮이면 주의할 점이 있다: **연도 필터를 PCA 앞에서 걸면 필터를 바꿀 때마다 유효 편수가 출렁여 refit이 반복되고, 배치가 계속 바뀐다.** 필터 변경에도 배치를 고정하고 싶다면 flow가 필터를 PCA 앞이 아니라 **`visual` 미들웨어에서 노드를 숨기는 방식**으로 적용하는 것을 권장한다 — 전체 코퍼스로 좌표를 만들고 표시만 거르는 것이며, 미들웨어가 정확히 이 용도로 설계돼 있다.

쓰는 필드는 네 개다. (`publicationDate`는 PCA가 읽지 않는다 — 시간축은 렌더러 몫이고, 렌더러는 결과에 실린 `paper` 참조에서 직접 읽는다.)

| 필드 | 용도 |
|---|---|
| `embedding: number[]` | PCA 입력 벡터 |
| `embeddingModel: string` | 기준 모델 선정 (아래) |
| `embeddingSucceeded: boolean` | 걸러내기 기준 |
| `sourceId: string` | 결과 좌표가 어느 논문 것인지 식별 |

### 기준 모델 선정

**서로 다른 모델의 임베딩은 절대 섞지 않는다.** 벡터 길이가 같아도 모델이 다르면 완전히 다른 공간의 좌표라서, 섞으면 기하학적으로 무의미한 결과가 그럴싸한 모습으로 나온다. 길이 검사만으로는 이를 잡을 수 없다 (768차원 모델이 여럿일 수 있다).

- 유효 후보들의 `embeddingModel` 중 **가장 많은 논문이 쓰는 모델**을 기준으로 삼는다
- 동률이면 **정렬(4절 처리 순서 1) 후 먼저 나온 모델**을 택한다 (결정성)
- 기준 모델이 아닌 논문은 `modelMismatch`로 제외한다

걸러내기는 **두 번 훑는다.** 표의 3번(`modelMismatch`)과 4번의 길이 검사는 기준(모델·길이)이 정해져야 판정할 수 있는데, 그 기준은 1·2번 통과자를 전부 본 뒤에야 정해지기 때문이다 — 1차 패스에서 기준을 정하고, 2차 패스에서 표의 순서대로 판정한다. 기준 길이의 최빈값은 **검사 1~3을 통과한(기준 모델과 일치하는) 후보의 `embedding.length`**로 구한다.

임베딩 모델 교체(재임베딩)가 진행 중인 시기에는 코퍼스에 두 모델이 공존하는 게 정상이다. 그때 이 규칙 덕에 그래프는 다수 모델 기준으로 그려지고, 나머지는 제외 수와 `usedModel`(3절)로 드러난다.

### 걸러내는 논문

다음에 해당하면 좌표를 만들지 않고 제외한다. **표의 순서대로 검사하고, 여러 항목에 해당해도 처음 걸린 항목에만 센다** (한 논문이 두 번 집계되지 않는다). 제외한 개수는 이유별로 결과에 담아 보고한다.

| 순서 | 이유 | 조건 |
|---|---|---|
| 1 | `malformed` | Paper의 꼴 자체가 아님 — PCA가 읽는 네 필드의 타입이 하나라도 어긋남: `sourceId`가 문자열이 아니거나 빈 문자열, `embedding`이 배열이 아님, `embeddingModel`이 문자열이 아님, `embeddingSucceeded`가 불리언이 아님 |
| 2 | `embeddingFailed` | `embeddingSucceeded === false` |
| 3 | `modelMismatch` | `embeddingModel`이 기준 모델과 다름 |
| 4 | `invalidVector` | `embedding`이 비었거나, 원소 중 유한한 숫자가 아닌 값(null·NaN·Infinity)이 있거나, 절댓값이 `1e100`을 넘거나, 길이가 기준 모델의 다른 논문과 다름 |
| 5 | `duplicateId` | 같은 `sourceId`의 논문이 앞에서 이미 나옴 — 첫 건만 쓴다 |

날짜(`publicationDate`)로는 거르지 않는다 — 시간축은 렌더러의 선택이므로, 시간을 안 쓰는 렌더러에게 날짜 없는 논문도 멀쩡한 데이터다. 날짜 처리는 렌더러 몫이다 (8절 4번).

각 항목이 필요한 이유:

- **`malformed`**: 저장된 JSON은 `Object.assign`으로 Paper에 복원되므로, 손으로 수정됐거나 깨진 파일이면 필드가 아예 없거나 타입이 다를 수 있다. 그런 객체가 계산까지 흘러가면 원인을 알기 어려운 지점에서 터진다. 입구에서 거른다.
- **`invalidVector`의 원소 검사**: JSON에서 읽은 배열은 타입 표기가 `number[]`여도 실제로는 `null`이 섞여 있을 수 있다. 걸러내지 않으면 NaN이 계산 전체에 조용히 번져 **모든 좌표가 NaN이 되는데 에러는 나지 않는다.**
- **`invalidVector`의 절댓값 상한**: `1e300` 같은 값은 유한해서 통과하지만 **분산 계산에서 제곱하는 순간 Infinity로 넘친다.** 그러면 최종 점검(4절)이 "계산 버그" 에러를 던지는데, 실은 데이터 문제라 오진이 된다. 상한 `1e100` 안의 값은 이 스펙의 어떤 중간 계산에서도 넘치지 않는다.
- **`invalidVector`의 길이 검사**: 같은 모델인데 길이가 다르면 파일 손상이다. 기준 길이는 기준 모델 논문들의 최빈값으로 하고, 동률이면 먼저 나온 길이를 쓴다.
- **`duplicateId`**: 논문의 발행일이 수정되면 같은 논문이 다른 날짜 폴더에 두 번 저장될 수 있다. 같은 `sourceId`로 좌표가 두 개 나가면 받는 쪽이 어느 것을 써야 할지 알 수 없다. (Paper에 갱신 시각이 없어 어느 쪽이 최신인지 판별할 수 없으므로, 첫 건 유지가 현재의 한계다.)

### 최소 개수

유효 논문이 **임계값 미만**이면 좌표를 만들지 않고 `PCAError`(3절)를 던진다.

- 임계값은 **15편**으로 잡는다 — 합의 기준은 25였지만 "개수는 조금 줄여도 괜찮다"고 함께 합의됐고, 경향성(덩어리 2~3개가 눈에 보이는 수준)에는 15면 충분하다. 코드에서 상수 하나로 조정할 수 있게 둔다
- 수학적 하한은 **3편**이다 (주성분 2개를 뽑는 데 필요한 최소). 임계값을 아무리 줄여도 이 밑으로는 내릴 수 없다
- 에러에는 입력 수·유효 수·제외 수(이유별)가 담겨 있어, 받은 쪽이 "왜 부족한지"를 그대로 안내할 수 있다
- 팀 합의("flow 함수가 에러를 내면 main에서 다시 할 수 있도록")대로, 이 에러는 `VisualizationFlow`가 삼키지 않고 main까지 올린다 — 재수집 여부는 main이 판단한다

## 3. 공개 인터페이스

`VisualizationFlow.run()`이 호출하는 형태다. **전부 `src/visualize/PCA.ts` 한 파일에 둔다.**

```ts
// 논문 한 편의 좌표 — 모든 렌더러가 공통으로 쓰는 최소 정보만 담는다
export interface PCAPoint {
	sourceId: string;
	x: number; // 제1주성분
	y: number; // 제2주성분
	paper: Paper; // 원본 논문 참조 — 렌더러가 크기(인용수)·인용 관계·시간축 등에 쓴다
}

// 결과가 맞게 나왔는지 확인하는 값들 (5절)
export interface PCAMetrics {
	explainedAxis1: number; // 제1축이 담은 분산 비율 (0~1)
	explainedAxis2: number; // 제2축이 담은 분산 비율 (0~1)
	explainedTotal: number; // 두 축 합계
	orthogonality: number; // 두 축의 내적. 0에 가까워야 정상
	meanX: number; // 결과 x 평균. 0에 가까워야 정상
	meanY: number; // 결과 y 평균. 0에 가까워야 정상
	converged: boolean; // 반복 상한 전에 수렴했는가
	iterations: number; // 실제로 돈 반복 횟수
}

// 제외된 논문 수 (이유별, 2절의 검사 순서와 동일)
export interface PCAExcluded {
	malformed: number;
	embeddingFailed: number;
	modelMismatch: number;
	invalidVector: number;
	duplicateId: number;
}

// fit이 찾은 축 일체. PCA가 내부에 보관했다가 다음 호출에서 재사용하며,
// 그 덕에 논문이 추가돼도 기존 점이 제자리에 남는다 (9절)
export interface PCABasis {
	mean: number[]; // 중심화에 쓴 평균 벡터 — 빠지면 같은 축으로도 투영이 어긋난다
	axis1: number[]; // 제1주성분
	axis2: number[]; // 제2주성분
	usedModel: string; // fit 당시 기준 모델
	dimension: number; // fit 당시 차원 수
	fittedCount: number; // fit 당시 유효 논문 수 — 20% 증감 판정의 기준
	fittedExplainedTotal: number; // fit 당시 설명 분산 합 — 품질 하락 관찰용
}

export interface PCAResult {
	points: PCAPoint[];
	metrics: PCAMetrics;
	excluded: PCAExcluded;
	usedModel: string; // 기준으로 삼은 임베딩 모델
	dimension: number; // 사용한 벡터 차원 수
	basis: PCABasis; // 이번 실행에 쓰인(또는 새로 만든) 축 — 무엇으로 그렸는지 확인용
	didFit: boolean; // 이번 실행에서 축을 새로 계산했는가
	fitReason: 'basis 없음' | '모델 변경' | '편수 20% 이상 변동' | '재사용'; // 판정 근거 (9절)
}

// 좌표를 만들 수 없을 때 던지는 에러. 수치를 필드로 들고 있어
// 받는 쪽이 메시지 문자열을 파싱할 필요가 없다.
export class PCAError extends Error {
	inputCount: number; // 입력 논문 수
	validCount: number; // 걸러낸 뒤 남은 수
	excluded: PCAExcluded; // 이유별 제외 수
	usedModel: string; // 기준 모델 — 재임베딩 과도기에 "왜 부족한지"를 설명하는 핵심 (후보가 전혀 없었으면 빈 문자열)
}

export class PCA {
	run(papers: Paper[]): PCAResult;
	resetBasis(): void; // 세션 캐시를 비운다 — 다음 실행은 반드시 새로 fit한다
}
```

각 필드가 인터페이스에 있는 이유:

- **`converged`·`iterations`** — 테스트 UI가 수렴 여부를 표시해야 하는데(6절), UI는 PCA 내부를 볼 수 없다. 결과에 담지 않으면 전달할 통로가 없다.
- **`usedModel`·`dimension`** — 재임베딩이 진행 중일 때 "지금 그래프가 어느 모델 기준인지"를 UI가 보여줄 수 있어야 한다. 없으면 "왜 논문 절반이 안 보이죠?"라는 문의가 사람에게 온다.
- **`paper`** — 팀 합의의 데이터 흐름이 `PCA -{(x, y), paper 객체}-> 시각화`다. 렌더러가 쓰는 정보(인용수에 따른 크기, 인용 관계, 피인용 여부, 시간축용 발행일)가 전부 Paper의 필드에 있으므로 좌표에 원본 참조를 함께 싣는다. 복사가 아니라 참조라 메모리 부담이 없고, 합의된 "시각화를 하면서 paper 객체 없애기"(그리기를 마친 뒤 참조 해제)도 이 참조를 놓는 것으로 이뤄진다.
- **`PCAError`** — 에러 메시지(한글 문장)에서 수치를 뽑아 쓰려면 문자열 파싱을 해야 하는데, 그건 메시지 문구만 바꿔도 UI가 깨지는 최악의 결합이다. 수치는 필드로 준다.
- **`basis`·`didFit`·`fitReason`** — 이번 실행이 무엇으로 그려졌는지 보고한다. 축의 보관과 재사용 판정은 PCA가 내부에서 하므로 호출 측이 할 일은 없다.

**`GraphData`는 건드리지 않는다.** 담당자가 정해지지 않았고, 좌표를 계산하는 일과 그래프 자료구조를 만드는 일은 책임이 다르다. `VisualizationFlow.run()`이 `PCAResult`를 받아 `Visualization`에 넘긴다.

`run()`은 **동기 함수**다. 계산만 하고 파일이나 네트워크를 건드리지 않으므로 `async`로 만들 이유가 없다. **입력은 변형하지 않는다** — 정렬(4절 처리 순서 1)은 복사본으로 하고, 넘겨받은 배열과 Paper 객체는 읽기만 한다. 호출 측의 배열 순서가 바뀌는 부작용을 만들지 않기 위함이다.

**축(basis)만은 인스턴스 안에 남는다** — 세션 캐시(9절). 같은 코퍼스를 다시 그릴 때 좌표를 고정하기 위한 것이며, 다른 코퍼스로 바꿔 그릴 때는 `resetBasis()`로 비운다. 그 외에는 이전 실행이 다음 실행에 영향을 주지 않는다.

### 알고리즘 교체 가능성

교체에는 두 층위가 있고, 대비 수준이 다르다.

**같은 PCA, 다른 계산법** (멱반복 → SVD·야코비·라이브러리 등) — **완전 지원.** 공개 인터페이스와 결과 어디에도 계산법이 드러나지 않는다. 4절의 멱반복은 구현 세부일 뿐이라 내부만 갈아끼우면 되고, 5절 지표는 어떤 올바른 PCA 구현에도 성립하므로 교체 후 검증도 같은 지표로 한다. 부호 고정(4절) 덕에 계산법을 바꿔도 축의 부호까지 같게 정규화되어 **좌표가 수치 오차 범위에서 동일하게 유지된다** — 교체가 사용자에게 보이지 않는다 (1·2축 분산이 뚜렷이 구분되는 데이터 기준. 두 축이 비등하면 4절대로 평면 안 회전의 여지는 남는다). basis(평균+축)도 계산법과 무관하다. 다이어그램의 "pca는 함수만 바꾸면 되므로 상관이 없다"가 이 층위이며, 완전히 보장된다.

**PCA가 아닌 다른 투영 알고리즘** (예: UMAP 계열) — 계약의 뼈대는 그대로 재사용된다: 논문 배열 입력 → 좌표+paper 출력, 2절 걸러내기 전체, 정렬·결정성 원칙, 최종 점검, `excluded`·`usedModel`·`dimension`·`didFit`. 반면 `PCAMetrics`의 설명 분산·직교성과 `PCABasis`의 평균+축은 PCA 고유 개념이라 그대로 옮겨지지 않는다. **두 번째 알고리즘이 실제로 생기는 시점에** `run(papers, basis?)` 모양의 공용 인터페이스(예: `Projector`)를 추출하고 flow의 필드 타입만 그리로 바꾸면 된다 — TypeScript 구조적 타이핑 덕에 기존 호출은 깨지지 않는다. 지금 미리 추상층을 만들지 않는 이유: 두 번째 구현이 없는 상태에서 가정으로 만든 추상은 실물이 오면 대개 맞지 않고, 단순성·가독성 원칙과도 부딪힌다.

## 4. 처리 순서

```
1. sourceId 사전순 정렬     입력 순서에서 결과를 분리 (아래 "결정성")
2. 유효 논문 걸러내기       (2절 기준, 기준 모델 선정 포함)
3. 평균 중심화              각 차원에서 평균을 빼 중심을 원점으로
4. 두 주성분을 동시에 계산   멱반복 + 매 반복 직교화 (아래)
5. 부호 고정                결과가 실행마다 뒤집히지 않게 (아래)
6. 투영 → x, y
7. 최종 점검                모든 좌표가 유한한 숫자인지 (아래)
8. 검증 지표 계산           (5절)
```

**basis가 주어지고 재사용 판정이 나면**(9절) 3~5를 건너뛰고 basis의 평균·축으로 6부터 진행한다 — `didFit: false`, `iterations: 0`, `converged: true`로 보고한다. 아래 3~5 설명은 fit이 일어나는 실행에만 해당한다.

### 주성분 계산 — 멱반복법 (동시 반복 + 한쪽 방향 직교화)

**주성분을 2개만 쓰므로 전체 고유값 분해를 하지 않는다.** 768개를 다 구해놓고 2개만 쓰는 것은 낭비이고, 코드도 훨씬 복잡해진다.

이렇게 동작한다.

1. 방향 벡터 두 개 `v1`, `v2`에서 시작한다 (초기값은 아래 "결정성" 참고)
2. 각각에 공분산을 곱한다
3. **`v2`에서 `v1` 방향 성분을 빼서 직교하게 만들고**, 둘 다 길이를 1로 되돌린다
4. 2~3번을 반복하면 `v1`은 분산이 가장 큰 방향으로, `v2`는 그다음 방향으로 수렴한다

**직교화는 한쪽 방향으로만 한다.** `v2`만 `v1`에 대해 직교화하고 `v1`은 건드리지 않는다. 그래야 `v1`이 최대 분산 방향을 차지하고 `v2`가 그다음을 차지하는 **축 순서가 구조적으로 보장**된다. 둘을 대칭으로 섞으면 어느 쪽이 1축으로 수렴할지 보장이 없다.

**공분산 행렬을 실제로 만들 필요가 없다.**

```
C·v = Xᵀ(X·v) / n
```

이 형태로 계산하면 768×768 행렬을 메모리에 올릴 일이 없다. 벡터 곱만 두 번 하면 된다. 행렬을 명시적으로 만들면 768²개의 값을 각각 N개 항의 합으로 누적하며 반올림 오차가 쌓이는데, 그것도 함께 피할 수 있다.

**왜 두 축을 동시에 돌리는가** — 1축을 먼저 구하고 데이터에서 그 성분을 뺀 뒤 2축을 구하는 방법도 있다. 하지만 그러면 **1축에 있던 오차가 2축으로 그대로 옮겨간다.** 매 반복마다 직교를 다시 맞추면 오차가 누적되지 않고 직교성이 계속 유지된다.

**수렴 판정** — 직전 반복의 방향과 새 방향의 **내적의 절댓값이 1에 충분히 가까워지면** 멈춘다. 절댓값으로 비교하는 이유: 수렴 과정에서 벡터의 부호가 일시적으로 뒤집혀도 방향 자체는 같으므로, 부호를 무시하지 않으면 다 수렴해놓고 계속 도는 버그가 된다. **반복 횟수 상한**(예: 300회)을 함께 두고, 상한 전에 수렴했는지와 실제 반복 횟수를 `PCAMetrics.converged`·`iterations`로 보고한다.

**수렴 후 두 축을 분산으로 확정한다 (교환 단계).** 시작 벡터가 우연히 제1주성분과 거의 수직이면 `v1`이 1축이 아니라 2축으로 먼저 수렴하는 병리가 가능하다 — 난수 시작이면 확률 0인 사건이지만, **결정론적 시작 벡터는 특정 코퍼스에서 항상 재현되는 버그로 만든다.** 그래서 수렴 후 두 축의 투영 분산을 비교해 큰 쪽을 1축으로 확정하고, 필요하면 교환한다. 부호 고정은 교환 뒤에 한다.

**두 축의 크기가 비슷하면 수렴이 느려진다.** 다만 이는 구현의 결함이 아니라 데이터의 성질이다. 1축과 2축의 분산이 비슷하다는 것은 그 평면 안에서 어느 방향을 1축으로 볼지가 원래부터 애매하다는 뜻이고, 어떤 방법을 써도 마찬가지다. **평면 자체는 정확하게 나오고 그 안에서 축이 조금 회전할 뿐**이므로, 좌표를 화면에 뿌리는 이 용도에서는 문제되지 않는다.

### 결정성 — 같은 입력이면 항상 같은 출력

수학적으로 고유벡터는 `+v`든 `−v`든 같은 답이다. 그래서 시작 벡터가 무작위면 **실행할 때마다 그래프가 좌우·상하로 거울 반전될 수 있다.** 사용자에게는 같은 데이터가 매번 다르게 보이는 버그로 느껴지고, 테스트 결과도 실행마다 달라져 비교할 수 없게 된다. 두 가지로 막는다.

1. **시작 벡터를 고정된 규칙으로 정한다.** 난수를 쓰지 않는다. 예: `v1`은 중심화된 데이터 중 처음으로 크기가 0이 아닌 벡터, `v2`는 그다음 벡터에서 `v1` 성분을 뺀 것. (둘 다 실패하는 극단적 경우는 표준 기저 벡터로 폴백)
2. **수렴 후 부호를 고정한다.** 각 축에서 절댓값이 가장 큰 성분이 양수가 되도록 필요하면 축 전체를 뒤집는다. 절댓값이 같은 성분이 여럿이면 앞 인덱스를 기준으로 한다.

여기에 더해 **처리를 시작하기 전에 입력을 `sourceId` 사전순으로 정렬한다** (처리 순서 1). 비교는 **코드포인트 기준**으로 한다 — `localeCompare`는 실행 환경의 로케일에 따라 순서가 달라져, 같은 코퍼스인데 기기마다 결과가 다른 식으로 결정성을 깨뜨린다. `File`이 논문을 어떤 순서로 주는지는 파일시스템·플랫폼에 따라 달라질 수 있는데, 정렬을 거치면 "먼저 나온 것"을 쓰는 모든 규칙 — 중복 제거의 첫 건, 기준 모델 동률, 기준 길이 동률 — 이 입력 순서가 아니라 사전순에 고정된다. 이 정렬 없이는 결정성 보장이 완성되지 않는다.

### 퇴화 케이스 — 분산이 없을 때

**1축부터 없는 경우** — 모든 벡터가 같으면(전체 분산 0) 주성분 자체를 정의할 수 없다. `PCAError`를 던진다.

**2축만 없는 경우** — 데이터가 한 방향으로만 퍼져 있으면(예: 3편이 일직선) 2축의 분산이 0이다. 이때 `v2`에 공분산을 곱하면 `v1`과 평행한 결과가 나오고, 직교화에서 그걸 빼면 영벡터가 된다. **영벡터를 길이 1로 정규화하는 순간 0으로 나누어 NaN이 터진다.** 최소 편수 조건으로는 못 막는다 — 15편이 모두 한 직선 위에 있을 수도 있다.

그래서 직교화 후 벡터 길이가 임계값 미만이면 **에러가 아니라 정상 종료**로 처리한다: 모든 `y`를 0으로 두고 `explainedAxis2 = 0`, `orthogonality = 0`으로 보고한다 (2축이 없으므로 잴 대상도 없다). 점들이 한 줄로 그려지는 것이 이 데이터의 정직한 모습이다.

이때 **basis의 `axis2`는 영벡터로 저장한다.** 재사용 시 y = (벡터−평균)·영벡터 = 0으로 자연히 유지되고, 9절의 유효성 검사도 "axis2가 전부 0인 경우"를 rank-1 basis로 정상 취급한다 — 단위길이 검사에 걸어 손상으로 오판하면 안 된다.

### 최종 점검과 에러 처리 원칙

**최종 점검** — 반환 직전에 모든 좌표(x·y)가 유한한 숫자인지 확인한다. 입력을 다 걸렀는데도 여기서 걸리면 계산 코드 자체의 버그이므로 에러를 던진다. "그럴싸해 보이는 깨진 좌표"가 조용히 그래프까지 흘러가는 것을 마지막 줄에서 막는다.

**에러를 던지는 경우는 세 가지뿐이며, 전부 `PCAError`다.**

| 경우 | 위치 |
|---|---|
| 유효 논문이 임계값(15편) 미만 | 걸러내기 직후 (2절) |
| 전체 분산 0 — 모든 벡터가 동일 | 주성분 계산 전 |
| 최종 점검 실패 — 좌표에 NaN·Infinity | 반환 직전 |

그 외에는 던지지 않는다. 좌표를 만들 수 있으면 만들고, 이상 신호는 지표(5절)에 드러낸다. **조용한 실패는 없다** — 좌표를 못 만드는 상황은 반드시 에러이고, 메시지는 한글로 쓰되 수치는 `PCAError`의 필드로 전달한다. 에러를 화면에 어떻게 보여줄지는 호출 측(`VisualizationFlow`와 UI)의 몫이다. 팀 합의도 같은 구조다 — "임베딩이 안 되어 있으면 flow 함수가 에러를 내고 main에서 다시 할 수 있도록 진행한다."

**인자 타입은 방어하지 않는다** — `papers`가 배열인지 같은 타입 수준의 검사는 TypeScript 계약에 맡긴다. 방어 코드를 겹겹이 두면 가독성만 나빠진다. 런타임에 실제로 깨질 수 있는 것, 즉 JSON에서 복원된 필드의 내용만 2절에서 거른다.

### 구현 메모

- **내부 계산은 `Float64Array`로 한다.** 중심화된 데이터와 방향 벡터를 일반 배열 대신 `Float64Array`에 담으면 내적 연산이 수 배 빠르고 GC 부담이 적다. 논문 수천 편 규모에서 체감된다. 도우미 함수(내적, 정규화 등)로 감싸면 가독성도 유지된다.
- **`noUncheckedIndexedAccess` 주의** — 이 프로젝트 tsconfig에서 인덱스 접근은 `Float64Array`를 포함해 전부 `number | undefined`가 된다. 안쪽 루프마다 `?? 0`을 도배하면 가독성이 무너지므로, 인덱스 접근을 도우미 함수 몇 개(내적·정규화·투영) 안에 가두고 그 안에서만 처리한다.
- 비용은 반복 1회당 `O(N × D)`이고 보통 수십 회 안에 수렴한다. 수백~수천 편 규모에서는 동기 실행으로 충분하다. 코퍼스가 만 편 단위로 커지면 그때 비동기 분할을 검토한다 (지금 하지 않는다).
- **수치 임계값 예시** — 수렴 허용오차 `1e-10`, 퇴화(영벡터) 판정 `1e-12`, basis 축 검증 허용오차 `1e-6`, 반복 상한 `1000`(두 축 분산이 비슷한 데이터는 평면 안 회전이 늦게 잦아들어 수백 회가 걸릴 수 있고, 반복 비용이 미미해 넉넉히 잡는다). 전부 상수로 두고 조정 가능하게 한다.
- **"전체 분산 0" 판정은 상대 비교로 한다** — 완전히 같은 벡터들도 부동소수점 때문에(같은 값 n개의 평균조차 1ulp 어긋난다) 분산이 정확한 0이 아니라 극소값으로 나온다. `=== 0` 비교는 이 경우를 영원히 못 잡으므로, 데이터 크기(평균 제곱 노름) 대비 상대 임계값(예: `1e-24`)으로 판정한다. 구현 검증에서 실제로 잡힌 함정이다.

## 5. 검증 지표

**좌표만 봐서는 PCA가 맞게 돌았는지 알 수 없다.** 수백 차원을 2차원으로 줄인 것이라 원본과 눈으로 비교할 방법이 없고, 고유벡터 계산이 틀려도 화면상으로는 그럴싸해 보인다. 그래서 결과에 항상 아래 값을 함께 담는다.

### 설명 분산 비율

각 주성분이 원본 데이터의 흩어짐을 몇 퍼센트 담고 있는지.

- **축의 분산** — 그 방향으로 데이터를 투영했을 때의 분산
- **전체 분산** — 각 차원의 분산을 모두 더한 값
- **비율** = 축의 분산 ÷ 전체 분산

```
1축  42.3%
2축  15.1%
──────────
합계 57.4%     ← 수백 차원을 2개로 줄이고 남은 정보량
```

이 값으로 잡을 수 있는 버그:

| 증상 | 원인 |
|---|---|
| 2축이 1축보다 크다 | 교환 단계(4절)까지 있으므로 구조적으로 나올 수 없다 — 나오면 분산 계산이나 교환 구현 자체가 잘못된 것 |
| 합이 100%를 넘는다 | 계산 오류 (수학적으로 불가능) |
| 음수가 나온다 | 분산 계산이 잘못됨 |
| 합이 지나치게 낮다 | 구현 오류이거나, 애초에 2D로 줄일 수 없는 데이터 |

### 축 직교성

주성분끼리는 서로 수직이어야 한다. 제1축과 제2축을 내적해 **0에 가까운지** 확인한다. 0에서 벗어나면 매 반복의 직교화가 제대로 되지 않은 것이다.

### 결과 평균

중심화를 거쳤으므로 결과 x·y의 평균도 **0 근처**여야 한다. 벗어나면 중심화 단계가 빠졌거나 잘못됐다.

### 재사용 실행에서는 해석이 달라진다 (`didFit: false`)

위의 "버그 신호" 해석은 **fit이 일어난 실행 기준**이다. basis를 재사용한 실행에서는 두 가지를 다르게 읽어야 한다:

- **결과 평균** — 중심화가 fit 당시의 평균(`basis.mean`)으로 이뤄지므로, 그 뒤 추가·제거된 논문 때문에 평균이 0에서 벗어나는 것이 **정상이다.** 버그가 아니라 데이터가 fit 시점에서 얼마나 이동했는지의 신호로 읽는다.
- **설명 분산** — 낡은 축으로 잰 값이라 fit 당시(`fittedExplainedTotal`)보다 낮게 나올 수 있다. "합이 지나치게 낮다"의 원인 목록에 **축이 낡음**이 추가되는 셈이고, 그 하락 폭이 9절 refit 기준(20%)을 조정하는 근거다.

직교성은 재사용 실행에서도 0이어야 한다 — 캐시된 축 자체가 직교이므로, 여기서 벗어나면 계산이 잘못된 것이다.

### 수렴 정보

`converged`가 `false`면 반복 상한에 걸려 끝난 것이다. 두 축의 분산이 비슷한 데이터에서 생길 수 있으며(4절), 좌표가 못 쓸 정도는 아니지만 축이 덜 안정적일 수 있다는 신호다.

> 위 지표들은 **실제 임베딩으로 돌릴 때도 계속 본다.** 논문 500편을 넣었는데 설명 분산이 3%로 나오면 "이 데이터는 2D로 담기 어렵다"는 신호이고, 이는 화면만 봐서는 알 수 없다.

## 6. 테스트 UI

`VisualizationView`의 `1. PCA` 칸에 붙인다. **새 파일을 만들지 않고 기존 뷰를 확장한다.** (담당 파트의 UI는 각자 만들기로 팀에서 합의했으므로 이 칸은 PCA 담당이 채운다.)

버튼은 셋이다 — 덩어리 검증(정답을 아는 합성 입력) / 재사용 검증(캐시 동작) / 실제 임베딩으로 실행(전 구간). 독립 실행 버튼은 시작 시 `resetBasis()`를 불러 앞 버튼의 축을 물려받지 않게 한다.

실행 후 화면에 보여줄 것 — 전부 `PCAResult`(또는 `PCAError`)에서 나온다:

- 입력 논문 수 / 유효 수 / 제외 수 (이유별, `excluded`)
- 기준 모델과 차원 (`usedModel`, `dimension`)
- 설명 분산 비율 (1축, 2축, 합계)
- 축 직교성, 결과 x·y 평균
- 수렴 여부와 반복 횟수 (`converged`, `iterations`)
- basis 사용 여부 (`didFit`, `fitReason`) — 재사용 경로를 탔는지 눈으로 확인하는 유일한 수단
- 좌표 결과 일부 (앞의 몇 건)
- 실행 시간 (UI에서 측정)

에러가 나면 `PCAError`의 필드(입력·유효·이유별 제외 수)를 그대로 표시한다. 메시지 문자열을 파싱하지 않는다.

## 7. 임시 요소 — 개발 중에만 사용, 이후 삭제

현재 임베딩 벡터를 실제로 만들 수 있는 경로가 없다. `Embedding` 클래스는 개발 중(`003-embedding-model`)이고, `FileTestModal`은 `embedding`을 빈 배열로 넣는다. 그래서 개발 기간에만 쓸 **합성 벡터**가 필요하다.

**임베딩 쪽 개발이 비슷한 수준에 이르면 그쪽과 붙여 확인하고, 아래 요소는 삭제한다.**

- **합성 벡터 생성기** — 768차원 벡터를 원하는 개수만큼 생성. **난수 시드를 고정해** 매 실행 같은 데이터가 나오게 한다 (결과 비교가 가능해야 검증이 된다). 생성하는 Paper는 **필수 필드를 전부 유효하게 채운다** — 특히 `embeddingModel`을 일정한 값(예: `"synthetic-test"`)으로 넣지 않으면 2절 걸러내기에서 전멸한다. `sourceId`는 **자릿수를 고정**한다(`test-001` 형식) — `test-10`이 `test-2`보다 사전순으로 앞서는 함정 때문에, 자릿수가 다르면 정렬 결과를 예측하기 어렵다
- **덩어리 검증** — 일부러 세 덩어리로 뭉친 벡터를 넣어, 결과도 세 덩어리로 갈라지는지 확인. 정답을 아는 입력으로 하는 가장 직관적인 확인이다

> ⚠️ 임시 코드는 **전부 `VisualizationView.ts`(UI 쪽) 안에 모아두고 삭제 예정 주석으로 표시한다.** `PCA.ts`에는 넣지 않는다 — 그쪽은 영구 코드만 있어야 삭제 작업이 스치지 않는다. 여러 파일에 흩어놓지 않는다.

5절의 검증 지표는 여기 해당하지 않는다. 그쪽은 실제 임베딩에서도 계속 쓴다.

## 8. 다른 담당자와 맞춰야 할 것

스펙 자체는 확정됐고, 아래는 **다른 사람의 코드에 달려 있어** 이쪽에서 정할 수 없다.

1. **`VisualizationFlow.run()`의 PCA 호출** — 시각화 flow 담당. 이 스펙은 3절의 `run(papers, basis?)`를 전제한다. 이대로 부르면 되고, 에러 표시가 필요하면 `PCAError`의 필드를 쓰면 된다. 좌표 고정(9절)을 살리려면 `result.basis`를 flow의 필드에 보관했다가 다음 호출에 넘기면 된다 — 그게 전부다.
2. **저장된 논문 전체를 읽는 방법** — File 담당. 현재 `File`에는 `readPapersByYear(year)`뿐이라 **어떤 연도가 존재하는지 알아낼 수단이 없다.** 시각화는 코퍼스 전체를 대상으로 하므로 연도 목록 조회나 전체 조회 함수가 필요하다. 개발 기간에는 합성 벡터를 쓰므로 막히지 않지만, 실제 데이터를 붙이는 시점에 요청해야 한다. **basis의 파일 저장**(재시작 후에도 좌표 유지, 9절)도 저장 위치·형식을 이쪽과 협의해야 한다.
3. **새로고침 설계가 확정될 때** — 담당 미정. 합의된 새로고침은 모든 노드를 arXiv ID로 재검색해 **인용 횟수·인용 여부만** 갱신한다 ("다른 점이 생길 때만 write"). **임베딩은 건드리지 않으므로 새로고침 후 PCA를 다시 돌려도 좌표는 그대로다** — 결정성(4절) 덕분에 같은 벡터는 항상 같은 좌표가 나온다. 달라지는 것은 크기·엣지 같은 시각 속성뿐이라 새로고침은 PCA 입장에서 안전한 작업이다. 단, 새로고침 설계가 나중에 임베딩까지 다시 만드는 쪽으로 바뀌면 재배치가 일어나므로 이 전제를 다시 확인해야 한다.
4. **임베딩 폴백과의 관계** — 임베딩 담당(`003-embedding-model`). `Embedding.embed()`는 절대 throw하지 않고, 모델 미설치·추론 실패 시 **해시 기반 폴백 벡터**(2048차원, `local-hashtf-v1-d2048`, `embeddingSucceeded: false`)를 돌려준다. 성공 시에는 768차원 `local-specter2-proximity-v1-d768`이다.

   PCA는 걸러내기 2번(`embeddingFailed`)에서 폴백을 제외하므로 **두 공간이 섞이는 일이 구조적으로 없다** — 폴백은 기준 모델 다수결에도 참여하지 않는다(투표 전에 걸러짐). 이 설계가 서로 맞물려 동작한다.

   **주의할 시나리오**: 모델이 설치되지 않은 상태로 수집하면 전 논문이 폴백이 되어 PCA에서 전부 제외되고 "유효 0편" 에러가 난다. 원인은 미설치인데 화면에는 숫자만 보이므로, 테스트 UI가 `excluded.embeddingFailed`가 지배적일 때 모델 설치 안내를 덧붙인다(6절).

5. **시간축(z) 구현** — 렌더러 담당. 시간축은 렌더러의 선택이라 PCA 계약에 없고, 쓰려면 결과에 실린 `paper.publicationDate`에서 직접 계산해야 한다. 그때의 함정을 넘겨둔다:
   - timestamp를 그대로 z로 쓰면 자릿수 차이(10자리 vs 한 자릿수) 때문에 **그래프가 종잇장처럼 납작해진다** — x·y가 실제로 퍼진 폭에 맞춰 정규화할 것
   - `"0225-11-07"` 같은 오타 날짜는 유효하게 파싱되는데, 최소~최대로 정규화하면 **극단값 하나가 나머지 전부를 한 평면에 눌러붙인다** — 정상 범위(예: 1900 ~ 현재+1년) 밖은 거를 것
   - 날짜 없는 논문을 아무 높이에나 두면 보는 사람이 그 높이를 발행 시점으로 읽는다 — **숨기거나 따로 표시할 것**
   - 전부 같은 날짜면 나눗셈이 성립하지 않으므로 z를 0으로 둘 것
   - 방향(이른 날짜가 아래인지 위인지)을 명시적으로 정할 것
   
   시간축을 쓰는 렌더러가 여럿이 되면 이 로직을 공용 헬퍼 하나로 두는 것을 권장한다 — 두 곳에 복제되면 반드시 어긋난다.

`GraphData`는 3절에서 다루지 않기로 확정했으므로 이 목록에서 제외한다.

## 9. basis와 refit

**basis** = fit이 찾은 축 일체(평균 벡터 + 두 축 + 메타데이터, 3절 `PCABasis`). 다음 호출에 그대로 넘기면 fit을 건너뛰고 투영만 하므로, **논문이 추가돼도 기존 점이 제자리에 고정된다.**

### 보관 방식 — PCA 내부의 세션 캐시

축은 **PCA 인스턴스가 직접 들고 있다.** 호출 측은 `run(papers)`만 부르면 되고 basis를 주고받을 필요가 없다.

- **메모리 전용이다.** 플러그인이 꺼지면 사라진다. 재시작 후에도 좌표를 유지하려면 파일 저장이 필요한데, 그건 PCA가 할 수 없는 일(Obsidian API를 몰라야 한다)이라 **지금 범위가 아니다.** 나중에 넣는다면 결과의 `basis`를 저장했다가 복원하는 경로를 호출 측에 두게 된다.
- **인스턴스는 플러그인 수명 내내 하나다** (`main.init()`의 `new PCA()`). 그래서 뷰를 닫았다 열어도 축이 유지된다 — 그게 목적이다.
- **다른 코퍼스를 그릴 때는 `resetBasis()`로 비운다.** 캐시가 하나뿐이라 앞서 본 코퍼스의 축이 남아 있는데, 편수가 크게 다르면 아래 판정이 알아서 refit하지만 **편수가 비슷한 다른 코퍼스는 판별할 단서가 없다.** 이때는 호출 측이 명시적으로 비워야 한다. 실제로 테스트 UI의 독립 실행 버튼들이 이 호출을 한다 — 넣지 않으면 앞 버튼의 축으로 뒤 버튼의 데이터를 투영하게 되어, 검증이 검증하려는 것을 확인하지 못한다.

### refit 판정 — 전부 자동, PCA 안에서

호출 측은 정책을 몰라도 된다. basis를 넘기면 PCA가 스스로 판단하고, 결과의 `didFit`·`fitReason`으로 무엇을 했는지 보고한다.

| 조건 | 동작 | `fitReason` |
|---|---|---|
| 캐시 없음 (첫 실행 또는 `resetBasis()` 직후) | fit | `"basis 없음"` |
| 캐시의 `usedModel`·`dimension`이 **이번 실행의 기준 모델·차원**과 불일치 | refit — 다른 공간의 축은 재사용할 수 없다 | `"모델 변경"` |
| 유효 편수가 fit 당시(`fittedCount`) 대비 **20% 이상 증감** | refit — 자동, 조건 없이 진행 | `"편수 20% 이상 변동"` |
| 그 외 | 재사용 — 기존 점 고정, `didFit: false` | `"재사용"` |

**사용자 조작은 필요 없다.** refit은 전부 자동이고, 그리기 전 계산 단계에서 일어나므로 화면에 떠 있는 그래프가 보는 도중 재배치되는 일도 구조적으로 없다 — 바뀌는 것은 지난 렌더링과 이번 렌더링 사이다. 수동 실행 체제(뷰 열기·버튼)에서는 그 순간이 항상 사용자 행동과 겹치므로 별도 안내 없이 조용히 진행해도 된다. (나중에 뷰 자동 재렌더가 생기면 그때 알림 한 줄을 추가한다. 자동 **수집** 계획(`Subscriptions.updateTime`, "몇 시/즉시" 합의)과 뷰 자동 **재렌더**는 별개이고, 후자는 아직 어디에도 없다.)

**왜 refit이 필수인가** — 재사용만 계속하면 축이 낡는다. 새 논문들이 새 주제로 뭉쳐도 옛 축에는 그 방향이 없어 **다른 주제가 같은 자리에 겹쳐 보이고**, 설명 분산이 조용히 떨어진다. 본질은 안정성(점 고정) vs 대표성(축이 현재 데이터를 담음)의 트레이드오프이며, 20% 증감 기준이 그 교환 비율이다. 품질 하락(재사용 실행에서 5절 설명 분산이 `fittedExplainedTotal`보다 크게 낮아짐)은 매 실행 공짜로 관찰되므로, 20% 기준을 조정할 근거로 쓴다.
