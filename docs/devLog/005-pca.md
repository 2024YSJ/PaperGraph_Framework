# 8월 4일 작업 기록 (다예 — 3순위 작업, PCA Class)

`docs/plan/primary_plan.md`의 3순위 "PCA Class 제작"(다예 담당) 구현 기록. 코드 작성 전에 계약과 규칙을 `docs/Structure/PCA_Spec.md`로 먼저 확정하고, 그 스펙대로 `src/visualize/PCA.ts`와 시각화 뷰의 PCA 테스트 칸을 구현했다.

**스펙 문서와 이 문서의 역할이 다르다.** `PCA_Spec.md`는 계속 유효한 계약(입력·출력·규칙)이라 설계가 바뀌면 갱신되고, 이 문서는 8월 4일에 무엇을 왜 그렇게 정했는지의 기록이라 이후 수정하지 않는다.

## 2026-08-04 확정 사항

### 출력은 `(x, y) + paper` 최소 계약 — z(시간축)는 PCA가 만들지 않는다

- 초안에서는 PCA가 `z`까지 계산해 넘기도록 썼다가, **렌더러와 PCA 계산 방식을 둘 다 갈아끼울 수 있어야 한다**는 전제에 따라 뺐다. `z = 시간`은 특정 렌더러의 선택이지 모든 렌더러의 공통 요구가 아니므로, 계약에 박으면 렌더러를 교체할 때마다 PCA 출력이 흔들린다.
- 팀 합의문의 표기(`PCA -{(x, y), paper 객체}-> 시각화`)와도 이쪽이 일치한다.
- 시간축이 필요한 렌더러는 함께 넘어가는 `paper.publicationDate`에서 직접 계산한다. 그때 밟을 함정 5가지(자릿수 차이로 인한 납작해짐, 오타 날짜의 극단값, 날짜 없는 논문, 전부 같은 날짜, 축 방향)는 스펙 8절 5번에 이관 지침으로 남겼다.
- 이 결정으로 `invalidDate` 필터와 `dateRange` 필드도 함께 제거했다 — 시간을 안 쓰는 렌더러에게 날짜 없는 논문은 멀쩡한 데이터인데 PCA가 미리 버리면 월권이다.

### 주성분 계산: 멱반복 + 한쪽 방향 직교화 (전체 고유값 분해 안 함)

- 주성분을 2개만 쓰므로 768개를 다 구하는 전체 고유값 분해는 낭비다. 멱반복은 코드가 훨씬 짧고, `C·v = Xᵀ(X·v)/n` 형태로 계산하면 **768×768 공분산 행렬을 메모리에 만들 필요조차 없다**(행렬 생성 시 누적되는 반올림 오차도 함께 피한다).
- 1축을 구하고 성분을 뺀 뒤 2축을 구하는 순차 방식 대신 **두 축을 동시에 돌리고 매 반복 재직교화**한다 — 순차 방식은 1축의 오차가 2축으로 그대로 옮겨간다.
- 직교화는 `v2`만 `v1`에 대해 하는 **한쪽 방향**이다. 대칭으로 섞으면 어느 쪽이 1축으로 수렴할지 보장이 없다.
- 정확도 검토: 계산법이 달라도 PCA의 축은 수학적으로 같다. 정확도를 가르는 실제 변수는 계산법이 아니라 **1·2축 분산의 간격**이고, 그 간격이 좁을 때는 어떤 방법을 써도 평면 안에서 축이 애매해진다(평면 자체는 정확). 시각화 좌표라는 용도에서 실용상 문제없다고 판단했다.

### 결정성: 같은 코퍼스면 항상 같은 그림

난수를 쓰면 실행마다 그래프가 거울 반전될 수 있다(고유벡터는 `+v`와 `−v`가 같은 답). 사용자에겐 버그로 보이고 테스트 비교도 불가능해지므로 네 겹으로 고정했다.

1. **입력을 `sourceId` 사전순 정렬** — `File`이 주는 순서는 파일시스템·플랫폼에 따라 달라질 수 있다. 비교는 **코드포인트 기준**으로 한다(`localeCompare`는 로케일에 따라 순서가 바뀌어 결정성을 깨뜨린다).
2. **시작 벡터를 고정 규칙으로** — 중심화된 데이터 중 처음으로 크기가 0이 아닌 벡터.
3. **수렴 후 교환 단계** — 시작 벡터가 우연히 1축과 거의 수직이면 축이 뒤바뀐 채 수렴할 수 있다. 난수 시작이면 확률 0인 사건이지만 **결정론적 시작은 특정 코퍼스에서 항상 재현되는 버그로 만든다.** 투영 분산이 큰 쪽을 1축으로 확정한다.
4. **부호 고정** — 절댓값 최대 성분이 양수가 되도록 뒤집는다(교환 뒤에 수행).

### 최소 편수: 15편 (합의 25에서 하향)

- 팀 합의는 "25편 이상일 때만 그래프를 그린다(경향성을 보여줘야 하므로)"였고 "조금 줄여도 괜찮다"는 단서가 함께 있었다. 덩어리 2~3개가 눈에 보이는 데는 15면 충분하다고 판단해 15로 잡고, 코드에서 상수 하나로 조정 가능하게 뒀다.
- 수학적 하한은 3편(주성분 2개를 뽑는 최소)이며 그 밑으로는 내릴 수 없다.
- 미달 시 `PCAError`를 던지고 `VisualizationFlow`가 삼키지 않고 main까지 올린다 — 합의문의 "flow 함수가 에러를 내면 main에서 다시 할 수 있도록"과 같은 구조다.

### 걸러내기 5종, 두 패스

`malformed` → `embeddingFailed` → `modelMismatch` → `invalidVector` → `duplicateId` 순으로 검사하고 **처음 걸린 항목에만 센다.** 3·4번은 기준(모델·길이)이 정해져야 판정할 수 있고 그 기준은 1·2번 통과자를 전부 봐야 정해지므로, 1차 패스에서 기준을 정하고 2차 패스에서 판정한다.

각 항목의 존재 이유:

- **`malformed`** — 저장된 JSON은 `Object.assign`으로 Paper에 복원되므로 손상 파일이면 필드 타입이 다를 수 있다. PCA가 읽는 네 필드를 전부 타입 검사한다.
- **`modelMismatch`** — **길이 검사만으로는 못 잡는다.** 768차원 모델이 여럿일 수 있고, 모델이 다르면 벡터 공간이 달라 섞으면 기하학적으로 무의미한 결과가 그럴싸하게 나온다. 그래서 기준은 길이가 아니라 **`embeddingModel`의 최빈값**으로 잡는다(길이 검사는 같은 모델 안의 파일 손상을 잡는 2차 방어로 강등).
- **`invalidVector`의 원소 검사** — JSON 배열은 타입 표기가 `number[]`여도 `null`이 섞일 수 있고, 걸러내지 않으면 NaN이 조용히 번져 **모든 좌표가 NaN이 되는데 에러는 안 난다.** 절댓값 상한(`1e100`)도 둔다 — `1e300`은 유한해서 통과하지만 분산 계산의 제곱에서 Infinity로 넘쳐 "데이터 문제"가 "계산 버그"로 오진된다.
- **`duplicateId`** — 발행일이 수정되면 같은 논문이 다른 날짜 폴더에 두 번 저장될 수 있다. Paper에 갱신 시각이 없어 어느 쪽이 최신인지 판별할 수 없으므로 첫 건 유지가 현재의 한계다.

### 검증 지표를 결과에 항상 담는다

**좌표만 봐서는 PCA가 맞게 돌았는지 알 수 없다** — 768차원을 2차원으로 줄인 것이라 원본과 눈으로 비교할 방법이 없고, 고유벡터 계산이 틀려도 화면상으로는 그럴싸해 보인다. 설명 분산 비율·축 직교성·결과 평균·수렴 정보를 `PCAMetrics`로 함께 반환한다. 계산 비용은 내적 몇 번 수준이라 사실상 0이다.

`converged`/`iterations`를 담는 이유는 UI가 PCA 내부를 볼 수 없기 때문이다 — 결과에 담지 않으면 전달할 통로가 없다.

### basis와 refit: PCA 내부의 세션 캐시로 확정 (2026-08-04 재결정)

- **basis** = fit이 찾은 축 일체(평균 벡터 + 두 주성분 + 메타데이터). 다음 실행에서 재사용하면 **논문이 추가돼도 기존 점이 제자리에 고정된다.**
- **평균 벡터를 반드시 함께 보관한다** — 빼먹으면 같은 축으로도 투영이 어긋나는 미묘한 버그가 된다.
- refit 판정은 **전부 PCA 안에서 자동**이다: 캐시 없음 → fit / 모델·차원 불일치 → refit / **편수 20% 이상 증감 → refit** / 그 외 재사용. 무엇을 했는지는 `didFit`·`fitReason`으로 보고한다.
- refit이 필수인 이유: 재사용만 계속하면 축이 낡아 **새 주제의 논문들이 옛 축에는 없는 방향이라 다른 주제와 같은 자리에 겹쳐 보이고**, 설명 분산이 조용히 떨어진다. 안정성(점 고정) vs 대표성(축이 현재 데이터를 담음)의 트레이드오프이며 20%가 그 교환 비율이다.

**보관 위치를 두 번 바꿨다.** 처음에는 PCA를 무상태로 두고 `run(papers, basis?)`로 주고받게 설계했다 — 상태를 호출 측에 두면 여러 코퍼스를 각각 안정적으로 유지할 수 있고, 파일 저장을 붙일 때 "캐시는 PCA 안 / 파일은 밖"으로 주인이 둘이 되는 문제도 피할 수 있어서다. 그러나 **파일 저장을 지금 범위에서 빼고 세션 캐시만 쓰기로 확정**되면서, 인자로 주고받을 주체가 사라져 내부 캐시로 전환했다.

전환하면서 `basis?` 인자와 함께 **basis 유효성 검사(`isBasisIntact` 등 약 45줄)도 삭제했다** — 캐시는 PCA가 직접 만든 것이라 손상될 수 없어 도달 불가능한 코드가 되기 때문이다. 나중에 파일 저장을 붙인다면 외부에서 온 basis는 신뢰할 수 없으므로 이 검사를 되살려야 한다.

**대가는 캐시 오염이다.** 인스턴스가 플러그인 수명 내내 하나(`main.init()`의 `new PCA()`)라, 편수가 비슷한 다른 코퍼스를 그리면 앞선 축이 그대로 재사용된다 — PCA는 "이게 같은 코퍼스인지" 판별할 단서가 없다. `resetBasis()`를 두어 호출 측이 명시적으로 비울 수 있게 했고, 테스트 UI의 독립 실행 버튼들이 실제로 이 호출을 한다. 넣지 않았을 때 **덩어리 검증이 앞 버튼의 축으로 다른 데이터를 투영해, 검증하려는 것을 확인하지 못하는 상태**가 실제로 재현됐다.

### 에러 정책: 세 경우만, 전부 `PCAError`

유효 편수 미달 / 전체 분산 0 / 최종 점검 실패(좌표에 NaN·Infinity). 그 외에는 던지지 않고 지표로 드러낸다. **조용한 실패는 없다.**

`PCAError`는 커스텀 클래스로 만들어 `inputCount`·`validCount`·`excluded`·`usedModel`을 **필드로** 들고 있다. 메시지 문자열에서 수치를 뽑아 쓰게 하면 **문구만 바꿔도 UI가 깨지는** 최악의 결합이 되기 때문이다.

### 파일 구조: `src/visualize/PCA.ts` 단일 파일 (약 630줄)

`AGENTS.md`의 "200~300줄이 넘으면 분리 고려" 기준을 넘지만, 지금은 나누지 않기로 했다.

- **팀 관례와 일치한다** — `Embedding.ts` 606줄, `SettingTab.ts` 521줄, `File.ts` 360줄이 모두 단일 파일이다(003도 "단일 파일"을 명시적 결정으로 기록했다). 이 파트만 쪼개면 오히려 프로젝트에서 튄다.
- **줄 수 대비 인지 부담이 낮다** — 그중 약 300줄이 `dot`/`normalize`/`subtract` 같은 5~15줄짜리 순수 함수 뭉치다. 상태가 없고 서로 얽히지 않아 위에서 아래로 읽으면 되고, 실제로 따라가야 할 로직은 `run()`(178줄)과 멱반복(105줄) 정도다.
- **지금 그을 만한 분리선이 없다** — 유일한 후보인 벡터 연산을 빼면 import가 12개 생기고, PCA 로직을 읽다가 계산 함수가 궁금할 때마다 파일을 오가야 한다. `noUncheckedIndexedAccess` 대응(`!` 단언)을 도우미 함수 안에만 가둔다는 설계 의도도 파일 경계를 넘으면 흐려진다.
- **나눠야 할 시점은 정해져 있다** — basis의 파일 저장이 붙으면 직렬화·검증·저장 정책이 들어오면서 "축을 계산한다"와 "축을 보관한다"의 책임이 갈린다. **그때 `PCABasis` 관련을 분리하면 깔끔한 선이 생긴다.** 지금 억지로 그으면 번잡해지기만 한다.

### 인자 타입은 방어하지 않는다

`papers`가 배열인지 같은 타입 수준 검사는 TypeScript 계약에 맡긴다. 방어 코드를 겹겹이 두면 가독성만 나빠진다. 런타임에 실제로 깨질 수 있는 것, 즉 JSON에서 복원된 필드의 내용만 거른다.

## 임베딩(003)과의 관계 — 서로 맞물린다

`Embedding.embed()`는 **절대 throw하지 않고**, 모델 미설치·추론 실패 시 해시 기반 폴백을 돌려준다.

| 상황 | embedding | embeddingModel | embeddingSucceeded |
|---|---|---|---|
| 모델 성공 | 768차원 | `local-specter2-proximity-v1-d768` | `true` |
| 폴백 | 2048차원 | `local-hashtf-v1-d2048` | `false` |

PCA는 걸러내기 2번(`embeddingFailed`)에서 폴백을 제외하므로 **두 공간이 섞이는 일이 구조적으로 없다.** 폴백은 기준 모델 다수결에도 참여하지 않는다(투표 전에 걸러짐). 양쪽이 따로 설계됐지만 둘 다 `embeddingSucceeded`를 계약으로 삼아 자연히 맞물렸다.

**주의할 시나리오**: 모델이 설치되지 않은 상태로 수집하면 전 논문이 폴백이 되어 PCA에서 전부 제외되고 "유효 0편" 에러가 난다. 원인은 미설치인데 화면에는 숫자만 보이므로, 테스트 UI가 `excluded.embeddingFailed`가 지배적일 때 모델 설치 안내를 덧붙이도록 했다.

## 검증

자동 검증 59건 전부 통과 (코어 39 + UI 배선 20). 검증 스크립트는 저장소에 넣지 않고 개발 중에만 사용했다(프로젝트에 테스트 프레임워크가 없고, 팀 관례는 UI 모달로 확인하는 방식이라 그에 맞췄다).

- **지표** — 축 순서, 분산 합 ≤ 1, 음수 없음, 직교성, 평균
- **결정성** — 재실행 좌표 완전 동일, 입력 순서를 뒤집어도 동일
- **덩어리 분리** — 정답을 아는 입력(3덩어리)이 결과에서도 갈라지는지
- **basis 캐시** — 8% 추가 시 기존 좌표 이동 **정확히 0**, 20% 이상 증감 시 refit, 모델 변경 시 refit, `resetBasis()` 후 재fit
- **걸러내기** — 5종 집계 정확도
- **에러 경로** — 편수 미달·분산 0·필드 보존
- **퇴화(rank-1)** — 일직선 데이터에서 y=0, NaN 없음, `axis2` 영벡터, 그 축의 재사용 허용
- **입력 불변성** — 호출자의 배열 순서가 바뀌지 않음

### 실제 임베딩 확인 (모델 설치 후, 21편 / 3주제)

```
임베딩 소요: 11.0초 (21편, 편당 522ms)
입력 21편 → 유효 21편, 제외 전부 0
기준 모델: local-specter2-proximity-v1-d768 (768차원)
설명 분산: 1축 42.5% + 2축 34.7% = 77.2%
직교성: -3.92e-17 / 결과 평균: x 2.64e-17 · y -5.35e-17
수렴: 완료 (47회 반복) / PCA 실행 시간: 4.8ms
덩어리 검증: 중심 간 최소 거리 0.531 ÷ 덩어리 안 평균 거리 0.020 = 26.3배
```

**26.3배 분리**가 핵심 결과다 — SPECTER2가 언어모델·컴퓨터비전·강화학습을 구분했고 PCA가 그 구분을 2D 좌표로 손실 없이 옮겼다는 뜻이다. 모델 미설치 상태에서는 폴백 21편이 전부 `embeddingFailed`로 제외되고 설치 안내가 뜨는 것까지 확인했다.

설명 분산 77.2%는 **이 테스트 데이터라서 높다** — 덩어리가 3개면 그 중심들은 수학적으로 2D 평면 위에 놓이므로 2축만으로 구조를 거의 완전히 담는다. 주제가 수십 개인 실제 코퍼스에서는 30~50%가 정상이며, 그때 낮다고 놀랄 필요 없다.

### 구현 중 잡힌 것 (스펙에 반영 완료)

문서 검토만으로는 안 나오고 **코드를 돌려야 나오는** 두 가지가 실제로 나왔다.

1. **반복 상한 300 → 1000** — 두 축의 분산이 비슷한 데이터(정삼각형 배치 덩어리)에서 평면 안 회전이 늦게 잦아들어 상한에 걸렸다. 반복 비용이 회당 미미해 넉넉히 잡았다.
2. **"전체 분산 0" 판정을 상대 비교로** — 완전히 같은 벡터들도 부동소수점 때문에(같은 값 n개의 평균조차 1ulp 어긋난다) 분산이 정확한 0이 아니라 극소값(~1e-29)으로 나온다. `=== 0` 비교는 이 경우를 영원히 못 잡으므로 데이터 크기 대비 상대 임계값으로 바꿨다.

### UI 표시에서 고친 것

실제 화면을 보고서야 드러난, **동작은 맞는데 사람이 오해하는** 부류 셋.

- 재사용 실행에서 `결과 평균`이 0을 벗어나는 것은 정상인데(fit 당시 평균으로 중심을 잡으므로) 화면이 그 맥락을 안 알려줘 버그로 보였다 → 안내 문구 추가.
- `수렴: 완료 (0회 반복)`이 모순처럼 읽혔다 → `해당 없음 (재사용이라 반복 계산을 하지 않음)`.
- 긴 줄(제외 사유)이 오른쪽으로 잘렸다 → 줄바꿈 클래스.

## 열린 항목 / 다음 담당자 참고

- **`VisualizationFlow.ts`에 `basis` 필드를 추가했다 (다른 담당자 파일 수정 — 확인 요망).** PCA는 상태를 남기지 않으므로 축을 보관할 곳이 호출 측에 필요한데, 그 자리가 없으면 좌표 고정 기능 자체를 쓸 수 없어 필드와 사용법 주석만 미리 넣어뒀다. **`run()`은 건드리지 않았다** — 흐름 구현은 담당자 몫이다. 필드가 불필요하다고 판단되면 지워도 PCA 쪽에는 영향이 없다.
- **`VisualizationFlow.run()` 담당** — `pca.run(papers)`로 부르면 된다. 좌표 고정(basis)을 살리려면 `result.basis`를 flow의 필드에 보관했다가 다음 호출에 넘기면 되고, **그게 전부다**(재사용/refit 판정은 PCA가 알아서 한다). 에러 표시가 필요하면 `PCAError`의 필드를 쓰고 메시지 문자열을 파싱하지 말 것.
- **`File` 담당** — 시각화는 코퍼스 전체를 대상으로 하는데 현재 `readPapersByYear(year)`뿐이라 **어떤 연도가 존재하는지 알아낼 수단이 없다.** 연도 목록 조회나 전체 조회 함수가 필요하다. basis의 파일 저장(재시작 후 좌표 유지)도 저장 위치·형식을 함께 협의해야 한다.
- **렌더러 담당** — 좌표 크기가 **0.2~0.5 수준**이다(SPECTER2 임베딩이 L2 정규화된 단위 벡터라서). 화면에 그릴 때 스케일을 키워야 하고, 시간축(z)을 붙일 때도 이 폭(약 1 단위)에 맞춰 정규화해야 한다. 시간축 구현 시 밟을 함정은 스펙 8절 5번 참고.
- **"최근 N년으로 그래프 제한" UI가 생기면** — 필터를 PCA 앞에서 걸면 필터를 바꿀 때마다 유효 편수가 출렁여 refit이 반복되고 배치가 계속 바뀐다. 배치를 고정하고 싶다면 **`visual` 미들웨어에서 노드를 숨기는 방식**으로 적용할 것(전체 코퍼스로 좌표를 만들고 표시만 거른다).
- **임시 요소 삭제 시점** — 테스트 UI의 합성 벡터 생성기·덩어리 검증·실제 임베딩 테스트용 모의 논문은 전부 `VisualizationView.ts` 안 한 블록에 모아두고 삭제 예정 주석을 달았다. 실제 수집 파이프라인(`CollectAndSave.run()`)이 완성되면 그 블록을 삭제하고 저장된 논문으로 확인하면 된다. **검증 지표(설명 분산·직교성·평균)는 여기 해당하지 않는다** — 실데이터에서도 계속 쓴다.
- **브랜치 번호** — 처음 `004-pca`로 만들었으나 `004-search-api-implementation`과 겹쳐 `005-pca`로 변경했다.
