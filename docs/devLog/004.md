# 8월 4일 작업 기록 (신빈 — 3순위 작업, API & SearchQuery Class)

`docs/plan/primary_plan.md`의 3순위 "API & SearchQuery Class 제작"(신빈 담당) 구현 기록.
스텁이던 `ArxivAPI`의 세 검색 함수를 실제 구현으로 교체하고, 통합 테스트 제보로 드러난
버그들을 기존 PaperGraph3D 프로젝트의 검증된 수집 파이프라인과 대조해 수정했으며,
003(임베딩)·005(PCA) 병합 후 세 파트가 실제로 이어지는지 확인하는 테스트 UI까지
연결했다.

## 2026-08-04 확정 사항

### `searchType` 값 3종 확정: `keyword` / `author` / `category`

- `keyword`(전체 검색, arXiv `all:`) / `author`(저자, `au:`) / `category`(분류, arXiv 전용
  값 체계 `cs.AI` 등). UI에 임시로 있던 `domain`은 `category`로 교체했다 — 이름 정리가
  아니라 **라이브 버그 수정**이었다(아래 "버그 수정" ② 참고).
- 구독 결합 규칙: API 하나당 조건 최대 3개, 전부 **AND**로 결합(넓히는 OR이 아니라
  좁히는 방향). 같은 타입 여러 개도 AND.

### API 객체의 정체성: "Paper를 완성하는 하나의 방법" (우빈 제안, 논의 후 채택)

- `API`는 "외부 서비스 하나"가 아니라 **"Paper를 완성하는 하나의 방법"**이다. 인용수처럼
  Paper에 필수인 정보를 arXiv가 못 주면, `ArxivAPI`가 반환 전에 다른 소스(Semantic
  Scholar)로 채워서 완성된 Paper를 내놓는다.
- 이 결정으로 인용수 보강을 별도 Middleware로 뺐다가 다시 API 안으로 합쳤다.
  **트레이드오프**: 다이어그램 원칙상으로는 `run()`의 미들웨어 단계가 더 맞지만, `run()`이
  미구현이라 그 방식으로는 지금 아무것도 검증할 수 없었다. API 통합 방식은 `run()`과
  무관하게 바로 동작·검증 가능하다.
- S2 조회는 논문 하나씩이 아니라 `POST /paper/batch`로 **최대 500건씩 한 번에** — 50건
  검색 시 요청 수가 50→1로 줄어 rate limit 위험이 낮아진다.

### 실패 처리 정책 3단계 — `ApiSupport.ts`로 공용화

1. **수집 자체 불가**(요청/파싱 실패, arXiv 에러 응답) → `throw` — 결과를 신뢰할 수
   없으므로 호출자가 실패로 판단해야 함 → `requestWithRetry` / `parseXml` /
   `assertNotErrorEntry`
2. **개별 논문 필드 누락** → 그 논문만 제외, 나머지는 정상 진행 → `hasRequiredFields`
3. **보강(인용수 등 선택 정보) 실패** → 예외 삼키고 플래그(`citationsKnown=false`)로 남겨
   다음 수집에서 재시도 → `enrichQuietly`

새 API(Semantic Scholar 독립 수집원, PubMed 등)를 추가할 때도 이 세 규칙을 그대로 따르면
실패 동작이 API마다 갈리지 않는다. 도구는 전부 `src/collect/ApiSupport.ts`에 있다.

### 재시도 정책: 429 외에 502/503/504도 일시 장애로 취급

- arXiv의 과부하/스로틀 응답은 429가 아니라 **503**이다. 429만 재시도하면 arXiv 스로틀이
  곧바로 "수집 실패 throw"가 된다. 재시도 대상을 `429, 502, 503, 504`로 넓혔다.
- 서버가 `Retry-After` 헤더를 주면 그 값을 따르고(최대 30초 클램프), 없으면 3초 간격.
- ⚠️ 기존 프로젝트에는 없는, 이 저장소 자체 판단의 확장이다(원본도 429만 재시도).

### 날짜 구간 수집: ascending 정렬 + 페이지네이션 + 커버리지 노출

- `SearchRecentPaper`/`Backfill`은 "구간 안의 논문을 빠짐없이"가 목적이므로 단발 조회로는
  안 된다. `start`를 올려가며 페이지를 넘긴다(`PAGE_SIZE=100`, 페이지 간 3초 =
  arXiv 권장 간격, `MAX_PAGES=20` 상한 = 최대 2000건).
- 정렬이 **ascending**인 게 핵심이다. descending + 상한이면 잘리는 건 구간의 오래된
  쪽인데 그 구멍은 커서 하나로 표현할 수 없어 이어받을 수 없다. ascending이면 훑은
  영역이 항상 `[from, coveredThrough]` 연속 구간이라, 잘려도 다음 패스가 그 지점부터
  이어받으면 아무것도 잃지 않는다 (기존 프로젝트 `arxivClient.ts`와 같은 구조).
- 실제로 어디까지 훑었는지를 `ArxivAPI.lastCoverage`(`{truncated, coveredThrough}`)로
  노출한다. **커서를 저장하는 건 `run()`의 책임**이라 여기서는 값만 제공한다 — 잘렸을 때
  `window.to`를 커서로 저장하면 못 본 구간을 봤다고 기록하게 되므로, `run()` 구현자는
  반드시 이 값을 쓸 것.
- `SearchBase()`는 "요즘 뭐 올라왔나"용 단발 조회(50건)라 최신순(descending) 유지.
- `MAX_RESULTS=50`(SearchBase)은 여전히 근거 약한 임의값 — 실제 부하를 보고 조정 필요.

### 기타 확정 판단

- **arXiv 엔드포인트는 `https://` 고정** — `http://`는 301 리다이렉트인데 `requestUrl`이
  안정적으로 따라간다는 보장이 없다.
- **`combineQueries`는 `SearchQuery.ts`에 배치** — AND로 묶인 조건들을
  `Paper.collectedQuery`용 대표값 1개로 합성하는 순수 함수. arXiv 지식이 없으므로
  `API.ts`가 아닌 신빈 담당 파일에 뒀다(002.md에서 확장 허용된 파일).
- **`Paper.ts`/`Middleware.ts`는 무수정** — 우빈 담당 파일. 공용 헬퍼를 잠깐 넣었다가
  되돌렸다.

## 버그 수정 (2026-08-04, 다예 제보로 시작)

다예가 api/임베딩/pca 통합 테스트 중 "API 쪽에서 오류난다"고 제보했다. 원인 확인 과정에서
004 파트 전체를 재검토해 총 9건을 수정했다. 핵심 구조: **쿼리를 만드는 쪽(①②)이 깨져
있는데, 깨진 걸 알려줘야 할 쪽(③)도 같이 깨져 있어서 결과가 틀려도 아무도 몰랐다** —
제보가 "왜 안 되는지 모르겠다"였던 이유다.

| # | 증상 | 원인 | 수정 |
|---|---|---|---|
| ① | 날짜 필터가 통째로 무시됨 | `+TO+`를 문자열에 직접 넣어 `URLSearchParams`가 `%2B`로 이중 인코딩 | 진짜 공백으로 바꾸고 `buildDateFilter()`로 일원화 |
| ② | 분류 조건 구독의 수집 전체 실패 | UI가 저장하는 `domain` vs API가 아는 `category` 불일치 → `formatTerm` throw | UI를 `category`로 교체 + `File.readSubscriptions()`에 기존 `domain` 값 마이그레이션 |
| ③ | 깨진 쿼리가 에러 없이 "가짜 논문 1건" 반환 | arXiv 에러 응답(`<entry>` 1개짜리 정상 피드)이 필수 필드 검사를 통과, `extractArxivId`의 `?? rawId` 폴백이 원본 URL을 sourceId로 흘림 | `assertNotErrorEntry()`로 throw(정책[1]), 폴백 제거로 빈 값 가드 실동작화 |
| ④ | 날짜 구간이 50건에서 조용히 잘림 | `start:0`/`max_results:50` 고정, 페이지네이션 없음 | 위 "날짜 구간 수집" 확정 사항대로 재구현 |
| ⑤ | `readTotalResults`가 태그 못 읽으면 0 반환 | `Number('')`는 NaN이 아니라 **0** → 첫 페이지 직후 "전 구간 완료"로 오판 | 빈 문자열을 먼저 걸러 -1 반환 |
| ⑥ | arXiv 스로틀(503)이 즉시 수집 실패 | 재시도 대상이 429뿐 | 위 "재시도 정책" 확정 사항대로 확대 |
| ⑦ | 특수문자 검색어가 쿼리 문법 파괴 | 값 안의 `"` 미제거, 공백 있을 때만 인용 | `"` 제거 + keyword/author 항상 인용 (기존 프로젝트 `searchClause` 이식) |
| ⑧ | S2 배치 응답이 밀리면 남의 인용수가 붙음 | `array[i]`↔`ids[i]` 위치 대응만 믿고 검증 수단 없음 | `fields`에 `externalIds` 추가, 응답의 arXiv id가 요청 id와 다르면 그 항목 폐기 |
| ⑨ | `searchType`이 `'toString'` 같은 값이면 함수가 쿼리에 박힘 | 맵 조회가 프로토타입 체인을 탐 (`Subscriptions.json`은 사용자 편집 가능 파일) | `typeof x !== 'string'` 검사로 교체 (`API.ts`/`File.ts` 양쪽) |

그 외: 빈/역전 날짜 구간(`from >= to`)은 호출 없이 즉시 종료(기존 프로젝트 가드 이식),
커버리지 커서는 `Math.max` 누적(정렬을 커서 정확성의 전제로 삼지 않기 위해), 설정탭
Backfill 날짜 입력의 종료일이 자정 파싱 탓에 통째로 빠지던 것을 +1일 보정으로 "당일
포함"으로 수정.

## 기존 PaperGraph3D 프로젝트와의 대조

수정의 근거를 확보하려고 기존 프로젝트의 수집 파이프라인 10개 파일(`arxivClient.ts`,
`scheduler.ts`, `backfill.ts`, `dedupe.ts`, `enrichment.ts` 등)을 받아 대조했다.

- **①은 원본이 맞았다** — 원본도 `submittedDate:[... TO ...]`로 진짜 공백을 쓴다.
  004가 손으로 `+`를 넣으면서 깨진 것.
- **④는 원본과 거의 동일하게 수렴** — `PAGE_SIZE=100`, 3초 간격 동일. 상한만 원본 10 vs
  우리 20.
- **③은 원본에도 있는 버그** — `arxivParser.ts`의 `?? idText.split('/').pop()` 폴백이
  같은 문제라, 원본도 arXiv 에러 응답을 가짜 논문으로 만든다. 우리 수정이 원본보다 낫다.
- **⑧의 원본 가드는 사실상 죽어 있었다** — `S2_FIELDS`에 최상위 `externalIds`가 없어
  검증 조건이 절대 안 걸린다. 우리는 필드를 실제로 요청해 살렸다.
- **"4일 보정"의 정체** (다예 질문에 대한 답): `scheduler.ts`의
  `ANNOUNCEMENT_LAG_MS = 4일`. 창을 뒤로 미는 게 아니라, 프론티어 창(`[lastCheckedAt,
  now]`)으로 커서를 전진시킨 뒤 **커서에 반영하지 않는 별도 재스캔 창**
  (`[frontier.from - 4일, frontier.from]`)을 한 번 더 훑어 늦게 색인된 논문을 건진다.
  신선도와 누락 방지를 동시에 얻는 구조. 이식하려면 커서 전진 주체(`run()`)와 중복
  제거(`dedupe.ts`)가 필요해 보류 — 아래 "열린 항목" 참고.

## 임베딩(003)·PCA(005)와의 연결

`origin/003-embedding-model`·`origin/005-pca`를 이 브랜치에 병합했다(충돌 없음). 병합 후
세 파트가 실제로 이어지는지 두 겹으로 확인했다.

1. **Obsidian 밖 통합 테스트** — 네트워크(`requestUrl`)만 가짜 arXiv Atom 응답으로 바꾸고
   나머지는 전부 실제 코드로: 수집 20편(S2 보강 20/20, HTTP 2회) → `Object.assign(paper,
   await embedding.embed(...))` → 폴백 벡터 2048차원·L2 norm 1.0·전부 상이 →
   `PCA.run()` 좌표 20개(설명 분산 0.83, 직교성 -2.75e-17, 39회 수렴). ⑧의 정렬 검증도
   응답을 한 칸 밀어 보내 20/20→**0/20 거부**되는 것까지 확인.
2. **Obsidian 안 테스트 UI** — 시각화 뷰 PCA 칸에 **"실제 arXiv 수집으로 실행"** 버튼
   추가. 005의 "실제 임베딩으로 실행(21편)"이 가짜 논문을 쓰는 것과 달리 진짜
   `SearchBase()` 결과를 임베딩→PCA로 흘려보낸다. 단계(수집/임베딩/PCA)마다 Notice 팝업
   한 줄 + 패널 상세 로그를 남겨 어느 단계에서 멈췄는지 보이게 했다.

설정탭도 정리했다: 임시 "arXiv API 테스트" 섹션(+`ArxivResultModal.ts`)을 삭제하고, 그
역할을 "수집"의 최근 논문/Backfill 버튼이 흡수 — `run()` 대신
`SearchRecentPaper()`/`Backfill()`을 직접 호출하고, 결과는 Notice 요약(편수·인용수 확인
현황·잘림 여부) + `console.debug` 전체 상세로 남긴다(`console.log`는 obsidianmd 린트가
금지 — 개발자 도구 콘솔의 로그 레벨 필터에서 Verbose/Debug를 켜야 보인다).

  2. **중복 제거**: 재스캔 창과 페이지네이션으로 창이 겹치므로 필수(원본 `dedupe.ts` 참고
     — run 내 seen-set + 저장 여부 확인).
  3. **커버리지 커서**: 수집 후 `api.lastCoverage`를 읽어 `truncated`면 `coveredThrough`를
     커서로 저장할 것 — `window.to`를 저장하면 못 본 구간이 영구 누락된다.
- **S2 API 키 배관이 아예 없다** — `Secret.getKey()` 호출처가 코드베이스에 0곳.
  `SettingTab`은 `subscriptions.secret = new Secret()`으로 빈 객체를 덮어쓴다.
  `File.readSecret()` → `Subscriptions.secret` → `ArxivAPI` 경로가 생겨야 S2 키를 쓸 수
  있다(현재는 익명 호출이라 429가 잦고 `enrichQuietly`가 삼켜 조용히 빈다). 기존 프로젝트
  `semanticScholarClient.ts`의 `withApiKey()` 참고.
- **`main.ts`의 커맨드 catch 주의** — `collect-recent`/`collect-backfill` 커맨드의
  `catch { new Notice('아직 구현되지 않음...') }`는 `run()` 구현 후에는 **진짜 수집
  실패까지 "미구현"으로 표시**하게 된다. `run()` 구현 시 이 catch를 실제 에러 표시로
  바꿀 것.
- 두 번째 API 추가 시 `ApiSupport.ts`의 3단계 정책 재사용 + `File.createApi` 스위치에
