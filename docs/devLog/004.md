# 8월 4일 작업 기록 (신빈 — 3순위 작업, API & SearchQuery Class)

`docs/plan/primary_plan.md`의 3순위 "API & SearchQuery Class 제작"(신빈 담당) 구현 기록.
스텁이던 `ArxivAPI`의 세 검색 함수를 실제 구현으로 교체하고, 통합 테스트 제보로 드러난
버그들을 기존 PaperGraph3D 프로젝트의 검증된 수집 파이프라인과 대조해 수정했으며,
003(임베딩)·005(PCA) 병합 후 세 파트가 실제로 이어지는지 확인하는 테스트 UI까지
연결했다.


### `searchType` 값 3종 확정: `keyword` / `author` / `category`

- `keyword`(전체 검색, arXiv `all:`) / `author`(저자, `au:`) / `category`(분류, arXiv 전용
  값 체계 `cs.AI` 등). UI에 임시로 있던 `domain`은 `category`로 교체했다 — 이름 정리가
  아니라 **라이브 버그 수정**이었다(아래 "버그 수정" ② 참고).
- 구독 결합 규칙: API 하나당 조건 최대 3개, 전부 **AND**로 결합(넓히는 OR이 아니라
  좁히는 방향). 같은 타입 여러 개도 AND.


### 실패 처리 정책 3단계 — `ApiSupport.ts`로 공용화

1. **수집 자체 불가**(요청/파싱 실패, arXiv 에러 응답) → `throw` — 결과를 신뢰할 수
   없으므로 호출자가 실패로 판단해야 함 → `requestWithRetry` / `parseXml` /
   `assertNotErrorEntry`
2. **개별 논문 필드 누락** → 그 논문만 제외, 나머지는 정상 진행 → `hasRequiredFields`
3. **보강(인용수 등 선택 정보) 실패** → 예외 삼키고 플래그(`citationsKnown=false`)로 남겨
   다음 수집에서 재시도 → `enrichQuietly`

새 API(Semantic Scholar 독립 수집원, PubMed 등)를 추가할 때도 이 세 규칙을 그대로 따르면
실패 동작이 API마다 갈리지 않는다. 도구는 전부 `src/collect/ApiSupport.ts`에 있다.

### 재시도 정책: 429 외에 502/503/504도 일시 장애로 취급

- arXiv의 과부하/스로틀 응답은 429가 아니라 **503**이다. 429만 재시도하면 arXiv 스로틀이
  곧바로 "수집 실패 throw"가 된다. 재시도 대상을 `429, 502, 503, 504`로 넓혔다.
- 서버가 `Retry-After` 헤더를 주면 그 값을 따르고(최대 30초 클램프), 없으면 3초 간격.
- ⚠️ 기존 프로젝트에는 없는, 이 저장소 자체 판단의 확장이다(원본도 429만 재시도).

### 날짜 구간 수집: ascending 정렬 + 페이지네이션 + 커버리지 노출

- `SearchRecentPaper`/`Backfill`은 "구간 안의 논문을 빠짐없이"가 목적이므로 단발 조회로는
  안 된다. `start`를 올려가며 페이지를 넘긴다(`PAGE_SIZE=100`, 페이지 간 3초 =
  arXiv 권장 간격, `MAX_PAGES=20` 상한 = 최대 2000건).
- 정렬이 **ascending**인 게 핵심이다. descending + 상한이면 잘리는 건 구간의 오래된
  쪽인데 그 구멍은 커서 하나로 표현할 수 없어 이어받을 수 없다. ascending이면 훑은
  영역이 항상 `[from, coveredThrough]` 연속 구간이라, 잘려도 다음 패스가 그 지점부터
  이어받으면 아무것도 잃지 않는다 (기존 프로젝트 `arxivClient.ts`와 같은 구조).
- 실제로 어디까지 훑었는지를 `ArxivAPI.lastCoverage`(`{truncated, coveredThrough}`)로
  노출한다. **커서를 저장하는 건 `run()`의 책임**이라 여기서는 값만 제공한다 — 잘렸을 때
  `window.to`를 커서로 저장하면 못 본 구간을 봤다고 기록하게 되므로, `run()` 구현자는
  반드시 이 값을 쓸 것.
- `SearchBase()`는 "요즘 뭐 올라왔나"용 단발 조회(50건)라 최신순(descending) 유지.
- `MAX_RESULTS=50`(SearchBase)은 여전히 근거 약한 임의값 — 실제 부하를 보고 조정 필요.

### 기타 확정 판단

- **arXiv 엔드포인트는 `https://` 고정** — `http://`는 301 리다이렉트인데 `requestUrl`이
  안정적으로 따라간다는 보장이 없다.
- **`combineQueries`는 `SearchQuery.ts`에 배치** — AND로 묶인 조건들을
  `Paper.collectedQuery`용 대표값 1개로 합성하는 순수 함수. arXiv 지식이 없으므로
  `API.ts`가 아닌 신빈 담당 파일에 뒀다(002.md에서 확장 허용된 파일).
- **`Paper.ts`/`Middleware.ts`는 무수정** — 우빈 담당 파일. 공용 헬퍼를 잠깐 넣었다가
  되돌렸다.

1. **Obsidian 밖 통합 테스트** — 네트워크(`requestUrl`)만 가짜 arXiv Atom 응답으로 바꾸고
   나머지는 전부 실제 코드로: 수집 20편(S2 보강 20/20, HTTP 2회) → `Object.assign(paper,
   await embedding.embed(...))` → 폴백 벡터 2048차원·L2 norm 1.0·전부 상이 →
   `PCA.run()` 좌표 20개(설명 분산 0.83, 직교성 -2.75e-17, 39회 수렴). ⑧의 정렬 검증도
   응답을 한 칸 밀어 보내 20/20→**0/20 거부**되는 것까지 확인.
2. **Obsidian 안 테스트 UI** — 시각화 뷰 PCA 칸에 **"실제 arXiv 수집으로 실행"** 버튼
   추가. 005의 "실제 임베딩으로 실행(21편)"이 가짜 논문을 쓰는 것과 달리 진짜
   `SearchBase()` 결과를 임베딩→PCA로 흘려보낸다. 단계(수집/임베딩/PCA)마다 Notice 팝업
   한 줄 + 패널 상세 로그를 남겨 어느 단계에서 멈췄는지 보이게 했다.

설정탭도 정리했다: 임시 "arXiv API 테스트" 섹션(+`ArxivResultModal.ts`)을 삭제하고, 그
역할을 "수집"의 최근 논문/Backfill 버튼이 흡수 — `run()` 대신
`SearchRecentPaper()`/`Backfill()`을 직접 호출한다. 결과는 처음엔 `console.debug`로만
남겼는데(`console.log`는 obsidianmd 린트가 금지), **DevTools 기본 필터가 Verbose를 숨겨
아무것도 안 보였다.** 게다가 "N편 수집" 숫자만으로는 날짜 필터나 페이지네이션이 실제로
동작했는지 알 수 없었다. `CollectResultModal`을 만들어 항목별 판정(날짜 필터 / 페이지네이션 /
커버리지 커서 / 인용수 보강 / sourceId 형식)으로 보여주고, 이를 위해
`CollectionCoverage`에 `pages`·`totalResults`를 추가했다 — 페이지네이션이 정말 돌았는지는
밖에서 관찰할 방법이 이것뿐이다.


## 열린 항목 / 다음 담당자 참고

- **`run()` 구현자(우빈)에게** — ⑤에 해당하는 세 가지가 전부 `run()`을 기다린다:
  1. **색인 지연 재스캔**: `Subscriptions.updateTime`을 커서로 쓰고, 위 "4일 보정" 구조
     (커서에 반영하지 않는 별도 재스캔 창)를 이식할 것.
  2. **중복 제거**: 재스캔 창과 페이지네이션으로 창이 겹치므로 필수(원본 `dedupe.ts` 참고
     — run 내 seen-set + 저장 여부 확인).
  3. **커버리지 커서**: 수집 후 `api.lastCoverage`를 읽어 `truncated`면 `coveredThrough`를
     커서로 저장할 것 — `window.to`를 저장하면 못 본 구간이 영구 누락된다.
  4. **`SearchRecentPaper`/`Backfill`에 넘기는 값을 검증할 것** — NaN은 이제 `collect()`가
     막지만(⑪), 애초에 UI/설정에서 잘못된 값이 들어오지 않게 하는 게 낫다.
- ** S2 API 키 배관 연결** — `File.readSecret()` → `ArxivAPI` 경로를
  만들었다. `ArxivAPI` 생성자가 `secret?: Secret`을 받아 인스턴스 필드로 보관하고,
  `fetchCitationBatch()`가 `secret.getKey('semanticScholar')`(상수
  `S2_SECRET_PROVIDER`로 export)가 있으면 `x-api-key` 헤더로 실어 보낸다. 없으면
  기존처럼 익명 호출 — 키는 선택 사항이지 필수가 아니다.
  - `File.createApi(apiName, querys, secret?)`에 secret 인자 추가, `File.readSubscriptions()`가
    `File.readSecret()`을 함께 읽어 `subscriptions.secret`과 복원되는 각 API 인스턴스에
    실어 보낸다(`Subscriptions.json` 자체엔 secret이 없으므로 매번 `Secret.json`에서
    새로 읽음).
  - 현재 유일한 실제 호출 경로인 두 테스트 UI(설정탭 수집 버튼, 시각화 뷰의 "실제 arXiv
    수집으로 실행")도 `await File.readSecret()`을 읽어 `ArxivAPI`에 넘기도록 갱신 —
    `run()`이 없어도 지금 당장 키를 등록하고 테스트할 수 있다. 키 사용 여부는 Notice에
    `(S2 키 사용)`으로 표시된다.
  - 키 등록은 `FileTestModal`의 기존 범용 Secret 폼(provider/key 텍스트 입력)에
    provider로 `semanticScholar`를 입력하면 된다 — 전용 UI를 새로 만들지 않았다.
  - Obsidian 밖 통합 테스트로 검증: 키 없을 때 S2 요청에 헤더 없음, 키 있을 때
    `x-api-key`에 정확한 값이 실리는 것 확인.
  - 기존 프로젝트 `semanticScholarClient.ts`의 `withApiKey()`와 같은 지점(요청 헤더에
    조건부로 키 추가)이지만, provider→key 조회는 이 저장소의 `Secret` 클래스 구조를 그대로 씀.
- **`main.ts`의 커맨드 catch 주의** — `collect-recent`/`collect-backfill` 커맨드의
  `catch { new Notice('아직 구현되지 않음...') }`는 `run()` 구현 후에는 **진짜 수집
  실패까지 "미구현"으로 표시**하게 된다. `run()` 구현 시 이 catch를 실제 에러 표시로
  바꿀 것.
- 두 번째 API 추가 시 `ApiSupport.ts`의 3단계 정책 재사용 + `File.createApi` 스위치에
  case 한 줄.
- SettingTab 구독 UI(`API 추가`/`조건 추가`)는 아직 `File.writeSubscriptions` 미연결.
- `CollectAndSave.run()` 완성되면 임시 테스트 UI(설정탭 수집 버튼의 직접 호출, 시각화
