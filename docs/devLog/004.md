# 8월 4일 작업 기록 (신빈 — API & SearchQuery 구현)

## 2026-08-04 확정 사항 (팀 논의로 정한 것들)

- **`searchType` 값 확정**: `keyword`(전체 검색, arXiv `all:`) / `author`(저자, `au:`) / `category`(분류, arXiv 전용 값 체계 `cs.AI` 등) 3종. UI에 임시로 있던 `domain`은 아직 `category`로 안 바뀐 상태.
- **구독 결합 규칙 확정**: API 하나당 조건 최대 3개, 전부 **AND**로 결합 (넓히는 OR이 아니라 좁히는 방향). 같은 타입 여러 개도 AND.
- **API 객체의 정체성 재정의 (우빈 제안, 논의 후 채택)**: `API`는 "외부 서비스 하나"가 아니라 **"Paper를 완성하는 하나의 방법"**. 인용수처럼 Paper에 필수인 정보를 arXiv가 못 주면, `ArxivAPI`가 반환 전에 다른 소스(S2)로 채워서 "완성된 Paper"를 내놓는다. 이 결정으로 인용수 보강을 별도 Middleware로 뺐다가 다시 API 안으로 합침 (아래 "시행착오" 참고).
- **실패 처리 정책 3단계 확정**:
  1. 수집 자체 불가(요청/파싱 실패) → `throw` — 결과를 신뢰할 수 없으므로 호출자가 실패로 판단해야 함
  2. 개별 논문 필드 누락 → 그 논문만 제외, 나머지는 정상 진행
  3. 보강(인용수 등 선택 정보) 실패 → 예외 삼키고 플래그(`citationsKnown=false`)로 남겨 다음 수집에서 재시도
  - 새 API를 추가해도 이 세 규칙을 그대로 따르면 실패 동작이 API마다 갈리지 않음.

## 진행한 작업

### `src/collect/API.ts`
- **`ArxivAPI.SearchBase()` / `SearchRecentPaper(hours)` / `Backfill(from, to)`** — 전부 스텁(`throw`)이었던 걸 실제 구현으로 교체. 셋 다 `private collect(dateFilter?)` 공통 경로를 타며 날짜 필터 유무만 다름.
- **`buildSearchQuery` / `formatTerm`** — `SearchQuery[]`를 arXiv 쿼리 문자열(`all:x AND au:y AND cat:z`)로 변환. 공백 있는 값은 구문 검색(`"따옴표"`) 처리.
- **`parseEntry`** — Atom XML `<entry>` 하나를 `Paper`로 매핑 (title/authors/abstract/sourceId/publicationDate/collectedApi/collectedQuery 등). 필수 필드(id/title/summary) 없으면 `undefined` 반환해 그 논문만 건너뜀 (실패 정책 2번).
- **`fetchAndParse`** — arXiv 호출 + XML 파싱을 묶은 함수. 실패 정책 1번(throw) 적용.
- **`enrichCitations` / `fetchCitationBatch`** — S2 인용수 보강. 논문 하나씩 호출하면 rate limit 위험이 커서, `POST /paper/batch`로 **최대 500건씩 한 번에** 조회하도록 구현 (50건 검색 시 요청 수가 50→1로 줄어듦). 실패해도 `citationsKnown=false`로 남김 (실패 정책 3번).
- **`extractArxivId`** — `".../abs/2501.12345v2"` → `"2501.12345"` (버전 접미사 제거).

### `src/collect/ApiSupport.ts` (신규 파일)
공용 실패 처리 도구 모음. 새 API를 추가할 팀원이 이 파일만 보면 규칙을 알 수 있게 문서화.
- **`requestWithRetry(param)`** — 429만 최대 3회 재시도(3초 간격), 그 외 4xx/5xx는 throw.
- **`parseXml(xmlText, source)`** — 파싱 실패(차단 페이지 등)를 "결과 0건"과 구분해 throw.
- **`hasRequiredFields(...values)`** — 필수 필드 검증.
- **`enrichQuietly(task)`** — 보강 작업 실패를 삼키는 래퍼.

### `src/collect/SearchQuery.ts`
- **`combineQueries(querys)`** 추가 — AND로 묶인 여러 조건을 `Paper.collectedQuery`용 대표 값 1개로 합성. arXiv 지식이 없는 순수 함수라 `API.ts`가 아닌 여기 배치 (신빈 담당 파일 + 002.md에서 확장 허용된 파일).

### `src/adapter/SettingTab.ts`, `src/adapter/ArxivResultModal.ts` (신규 파일)
- "arXiv API 테스트" 섹션 추가 — `CollectAndSave.run()` 완성 전에 `ArxivAPI.SearchBase()`를 단독으로 검증할 수 있는 임시 UI. 결과는 저장하지 않고 `ArxivResultModal`로 필드별 매핑 확인 + JSON 클립보드 복사만 제공.
- 저장하지 않는 이유: "흐름 제어(수집→미들웨어→저장)는 `run()`만 담당한다"는 원칙(001.md) 유지.

## 확정한 판단들 (팀원 확인 필요 시 참고)

1. **arXiv 엔드포인트는 `https://`로 고정.** `http://`는 301로 리다이렉트되는데 `requestUrl`이 이를 안정적으로 따라간다는 보장이 없어 처음부터 https 사용.
2. **S2 인용수 보강은 미들웨어가 아니라 API 안에 통합.** 원래 `run()`의 `미들웨어(forEach)` 단계로 분리하려 했으나(다이어그램상 그게 원칙에 더 맞음), 우빈이 "API=Paper를 완성하는 방법"이라는 해석을 제시해 논의 후 이쪽으로 결정. **트레이드오프**: `run()`이 아직 미구현이라 미들웨어 방식이면 지금 아무것도 검증할 수 없었는데, API 통합 방식은 `run()`과 무관하게 지금 바로 동작·검증 가능. 팀 확인 시 이 결정이 맞는지 짚어볼 것.
3. **`Paper.ts`는 건드리지 않음.** 리팩터링 과정에서 공용 헬퍼(`createCollectedPaper`)를 잠깐 `Paper.ts`에 넣었다가, 우빈 담당 파일이라는 걸 확인하고 되돌림. `Paper` 관련 공용 로직이 필요하면 `API.ts` 안에 두거나 우빈과 상의 후 옮기기로.
4. **`Middleware.ts`엔 결국 아무것도 추가 안 함.** 인용수 보강을 여기 넣었다가(`CitationEnrichMiddleware`) 3번 결정으로 빼서 다시 원상복구. `Middleware`는 여전히 인터페이스만 있는 빈 확장점.
5. **`MAX_RESULTS = 50`은 근거가 약한 임의값.** 팀 합의나 스펙에서 나온 숫자가 아니라 감으로 정함. 실제 임베딩/저장 부하나 구독당 신규 논문 수를 보고 나중에 조정 필요.

# 통합 테스트 후 버그 수정 (2026-08-04, 다예 제보)

다예가 api/임베딩/pca 통합 테스트 중 "API 쪽에서 오류난다"고 제보. 확인 결과 날짜 필터의
`+TO+` 문제가 맞았고, 이걸 보는 김에 004 파트 전체를 훑어 4건을 더 찾아 함께 고쳤다.

## 문제의 구조

**쿼리를 만드는 쪽(①②)이 깨져 있는데, 깨진 걸 알려줘야 할 쪽(③)도 같이 깨져 있어서
결과가 틀려도 아무도 모르는** 상태였다. 제보가 "왜 안 되는지 모르겠다"였던 게 ③ 때문이다.
그래서 ①②③은 세트로 고쳤다.

## 고친 것

### ① 날짜 필터 `+TO+` 이중 인코딩 — `API.ts`

`submittedDate:[...+TO+...]`처럼 `+`를 문자열에 직접 넣고 있었다. 그런데 `buildUrl()`의
`URLSearchParams`는 **값 안의 `+`를 리터럴 플러스로 보고 `%2B`로 이스케이프**한다.
결과적으로 arXiv에는 `[202601010000%2BTO%2B202601020000]`이 전달돼 range 문법으로
인식되지 못했다 → `SearchRecentPaper`/`Backfill`의 날짜 필터가 통째로 무시됨.

원래 `+`는 "URL 인코딩된 공백"이므로, **진짜 공백을 넣고 인코딩은 `URLSearchParams`에
맡기는 게** 맞다. 두 호출부가 같은 실수를 반복하지 않도록 `buildDateFilter()`로 모았다.

```
AS-IS: search_query=...submittedDate%3A%5B202601010000%2BTO%2B202601020000%5D  (깨짐)
TO-BE: search_query=...submittedDate%3A%5B202601010000+TO+202601020000%5D      (정상)
```

### ② `domain` / `category` 불일치 → 수집 전면 실패 — `SettingTab.ts`, `File.ts`

위 "남은 일"에 적어둔 `domain` → `category` 교체가 **단순 이름 정리가 아니라 라이브
버그**였다. UI 드롭다운이 `domain`을 `searchType`으로 저장하는데 `ARXIV_FIELD_PREFIX`는
`category`만 알아서, 분류 조건으로 구독을 만들면 `formatTerm()`이
`Unknown searchType`으로 throw → 실패 정책[1]에 따라 **그 구독 수집 전체가 실패**했다.

- `SettingTab.ts`: `ConditionType`과 드롭다운을 `category`로 교체, 라벨은 '분류'
- `File.ts`: 이미 `domain`으로 저장된 `Subscriptions.json`이 남아 있으면 복원 시점에
  똑같이 터지므로, `readSubscriptions()`에 `domain` → `category` 정규화를 추가

### ③ arXiv 에러 응답이 정상 Paper로 둔갑 — `API.ts`

arXiv는 잘못된 쿼리에 HTTP 에러가 아니라 **`<entry>` 1개짜리 "정상" Atom 피드**를 준다
(`<title>Error</title>`, `<id>http://arxiv.org/api/errors#...`). id/title/summary가 모두
채워져 있어 `hasRequiredFields()`를 통과하고, `extractArxivId()`가 `/abs/`가 없을 때
`?? rawId`로 **원본 URL을 그대로 흘려보내서** `sourceId: "arxiv:http://arxiv.org/api/errors#..."`
인 가짜 Paper가 만들어졌다. (그 바로 아래 `if (!arxivId)` 가드는 fallback 때문에 절대
걸리지 않는 **사실상 죽은 코드**였다.)

- `assertNotErrorEntry()` 추가 — 에러 entry를 만나면 `<summary>`를 사유로 담아 throw (정책[1])
- `extractArxivId()`는 `/abs/`가 없으면 `''` 반환 → 위 가드가 실제로 동작

### ④ 날짜 구간 수집이 50건에서 조용히 잘림 — `API.ts`

`start:'0'` / `max_results:50` 고정에 페이지네이션이 없고 `sortOrder`가 `descending`이라,
구간에 500건이 있어도 **최신 50건만 남고 450건이 말없이 사라졌다.** Backfill이 특히 크게
겪는 문제이고, `SearchRecentPaper`도 같은 구조였다.

- `buildUrl(dateFilter, start, maxResults)`로 파라미터화
- 날짜 구간 경로는 `collectPaged()`로 분리 — `<opensearch:totalResults>`와 응답 entry 수를
  보며 끝까지 페이지를 넘긴다 (`PAGE_SIZE=100`, 페이지 간 `delay(3000)` = arXiv 권장 간격)
- `MAX_PAGES=20`(최대 2000건) 상한. 상한에 걸리면 **조용히 자르지 않고 `console.warn`으로
  잘렸다는 사실을 남긴다** — 그러지 않으면 ④를 그대로 반복하는 셈이라서
- 마지막 페이지 판정에 `papers.length`가 아니라 원본 `entry` 개수를 쓴다. 정책[2]로
  건너뛴 항목이 있으면 `papers.length`가 줄어들어 오판하기 때문
- `SearchBase()`는 "맛보기" 단발 조회이므로 기존 50건 동작 그대로 유지 (`collectOnce()`)

### ⑥ arXiv 스로틀(503) 재시도 누락 — `ApiSupport.ts`

`requestWithRetry()`가 429만 재시도했는데 **arXiv의 과부하/스로틀 응답은 503**이라,
arXiv 쪽 일시적 스로틀이 곧바로 "수집 실패 throw"가 됐다. ④로 호출 횟수가 늘어나 더 자주
걸릴 수 있어 함께 고쳤다.

- 재시도 대상을 `429, 502, 503, 504`로 확대
- 서버가 `Retry-After`를 주면 그 값을 따르고(최대 30초로 클램프), 없으면 기존 3초 간격
- 마지막 시도 뒤에는 불필요하게 기다리지 않도록 정리

## 이번에 안 고친 것 (팀 논의 필요)

- **⑤ `SearchRecentPaper(hours)`의 고정 시간 창** — arXiv 색인 지연 때문에
  `[now-hours, now]` 창으로 폴링하면 창이 지나간 뒤 색인된 논문이 **영구 누락**된다.
  `Subscriptions.updateTime`(이미 있지만 아무도 안 씀)을 `from` 앵커로 쓰고 성공 시
  갱신하는 구조가 맞는데, 갱신 주체가 `CollectAndSave.run()`(우빈, 미구현)이라 보류.
- **⑦ S2 인용수 보강의 API 키** — 조사해보니 "키가 있는데 안 쓴다"가 아니라 **배관이 아예
  없다**: `Secret.getKey()`를 호출하는 코드가 코드베이스에 한 군데도 없고,
  `SettingTab.ts`는 `subscriptions.secret = new Secret()`으로 저장된 키를 읽는 대신 빈
  객체로 덮어쓴다. `File.readSecret()` → `Subscriptions.secret` → `ArxivAPI` 경로를
  새로 만들어야 하는데 `Subscriptions`/`CollectAndSave`가 우빈 파트라 보류.
  현재는 S2를 익명 호출하므로 429가 잦고, `enrichQuietly`가 삼켜 `citationsKnown=false`로
  조용히 남는다.
- **⑧ `formatTerm()`의 따옴표 처리** — 공백이 있을 때만 따옴표로 감싸고 값 안의 `"`는
  이스케이프하지 않아 `foo"bar` / `foo)` 같은 값이 쿼리를 깨뜨릴 수 있다. 특수문자를
  넣어야 재현되므로 급하지 않아 보류.

  - `SearchBase()` 회귀 (50건, 필드 매핑 정상)

# 기존 프로젝트 대조 후 추가 반영 (2026-08-04)

다예가 "arXiv 등록 지연 보정이 원래 있지 않았냐"고 물어, 기존 PaperGraph3D 프로젝트의
수집 파이프라인 파일을 받아 대조했다 (`arxivClient.ts`, `arxivParser.ts`, `scheduler.ts`,
`backfill.ts`, `dedupe.ts`, `enrichment.ts`, `semanticScholarClient.ts`,
`semanticScholarParser.ts`, `subscriptionStore.ts`, `promotion.ts`).

## 4일 보정의 정체 (질문에 대한 답)

`scheduler.ts`에 있었다:

```ts
const ANNOUNCEMENT_LAG_MS = 4 * 24 * 60 * 60 * 1000; // 4 days (FR-041, Decision 38)
```

**창을 4일 뒤로 미는 방식이 아니다.** 프론티어 창은 `[lastCheckedAt, now]`로 그대로 두고
커서를 전진시킨 뒤, **별도의 재스캔 창**을 한 번 더 훑는다:

```ts
// computeLagOverlapWindow
from: Math.max(frontierWindow.from - ANNOUNCEMENT_LAG_MS, floor),
to:   frontierWindow.from,
```

이 두 번째 결과는 **커서에 반영하지 않는다** (`no recordChecked`, 실패해도 무시). 논문만
건지고 버린다. 그래서 신선도(창이 `now`까지 감)와 누락 방지(최근 4일을 매 패스 재확인)를
동시에 얻는다. 창을 미는 방식은 신선도를 포기하므로 이쪽이 낫다. 이때 생기는 중복은
별도 `dedupe.ts`(run 내 seen-set + 이미 저장됐는지 확인)가 처리한다.

→ 우리 쪽 ⑤를 해결할 때 이 구조를 그대로 가져오면 된다. 다만 `lastCheckedAt`(=
`Subscriptions.updateTime`) 전진과 dedup이 모두 `CollectAndSave.run()` 몫이라 여전히
우빈 파트다.

## 대조로 확인된 것

- **① 수정이 맞았다.** 원본 `arxivClient.ts`도 `submittedDate:[... TO ...]`로 **진짜 공백**을
  쓴다. 원본은 `encodeURIComponent`(공백→`%20`), 우리는 `URLSearchParams`(공백→`+`)를
  쓸 뿐 둘 다 정상이다. 004는 거기에 손으로 `+`를 넣어서 깨진 것.
- **④ 페이지네이션도 거의 동일하게 수렴했다.** 원본 `PAGE_SIZE=100`,
  `INTER_PAGE_DELAY=3000ms` — 우리와 같다. `MAX_PAGES`만 원본 10, 우리 20.
- **⑥(503 재시도)은 원본에 없다.** 원본도 429만 재시도한다. 우리 쪽 판단으로 추가한
  것이며 원본 동작과 다르다는 점을 명시해 둔다.
- **③(에러 응답)은 원본에도 있는 버그다.** `arxivParser.ts`의
  `?? idText.split('/').pop()` 폴백이 004의 `?? rawId`와 같은 문제라, 원본도 arXiv 에러
  응답을 가짜 논문으로 만든다. 우리 수정이 원본보다 낫다.

## 이번에 추가로 고친 것

### ⑦ 정렬을 ascending으로 — `API.ts`

원본 `arxivClient.ts`는 `sortOrder=ascending`을 쓰고 `{ truncated, coveredThrough }`를
반환한다. 이유가 있다:

- `descending` + 페이지 상한 → 잘리는 건 구간의 **오래된 쪽**. 그 구멍은 "어디까지 봤다"는
  값 하나로 표현할 수 없어 이어받을 수가 없다 (그래서 직전 커밋에서 경고만 남겼던 것).
- `ascending` → 훑은 영역이 항상 `[from, coveredThrough]`라는 **연속 구간**. 잘려도 다음
  패스가 그 지점부터 이어받으면 아무것도 안 잃는다.

`collectPaged()`를 ascending으로 바꾸고, 각 페이지의 `<published>` 최댓값을 커서로 모아
`ArxivAPI.lastCoverage`(`{ truncated, coveredThrough }`)로 노출한다. 커서를 실제로
저장하는 건 `run()`의 책임이라 여기서는 값만 제공한다. `SearchBase()`는 "요즘 뭐 올라왔나"를
보는 단발 조회라 최신순(descending) 유지.

### ⑧ `formatTerm()` 따옴표 처리 — `API.ts`

원본 `searchClause`를 그대로 옮겼다. 값 안의 `"`를 제거하고(안 그러면 값이 구문 검색의
닫는 따옴표를 먼저 끝내버린다), keyword/author는 **길이와 무관하게 항상** 감싼다.
기존의 "공백이 있을 때만 감싸기"는 `foo)`처럼 공백 없이도 문법을 깨뜨리는 값을 놓쳤다.
`cat:`은 `cs.AI` 같은 고정 토큰이라 감싸지 않는다 (원본과 동일).

### ⑨ S2 배치 정렬 검증 — `API.ts` (신규 발견)

원본 `enrichment.ts`에 긴 주석과 함께 방어 로직이 있었다: **S2가 배치 결과를 재정렬하면
A 논문의 인용수가 B 논문에 조용히 붙는다.** 004는 `array[i]`를 `ids[i]`에 그냥 대응시키고
있었고, `fields=citationCount`만 요청해서 **검증할 방법 자체가 없었다.**

- `fields`에 `externalIds`를 추가해 응답이 자기 arXiv id를 밝히게 하고,
  그게 우리가 물어본 id와 다르면 그 항목을 버린다 (버전 접미사는 `stripArxivVersion`으로 제거).
- 버려진 논문은 `citationsKnown=false`로 남아 다음 수집에서 재시도된다([3] 정책) —
  틀린 값을 넣는 것보다 낫다.
- **원본의 같은 가드는 사실상 죽어 있었다**: `S2_FIELDS`에 최상위 `externalIds`가 없어
  (`references.externalIds`만 있음) `paper.arxivId`가 항상 `undefined`라 조건이 걸리지
  않는다. 우리 쪽은 필드를 요청해서 실제로 동작하게 했다.

## 전체 재검토에서 잡은 것 (2026-08-04, 위 변경들 반영 후)

새로 추가한 코드가 앞서 고친 것과 충돌하지 않는지 처음부터 다시 읽었고, **직접 넣은
버그 1건**과 잠재 구멍 2건을 찾았다.

### (버그) `readTotalResults`가 태그를 못 읽으면 -1이 아니라 0을 반환

`text()`가 빈 문자열을 주는데 **`Number('')`는 NaN이 아니라 `0`**이라,
`Number.isFinite(0) && 0 >= 0`을 통과해 "전체 0건"으로 해석됐다. 그 결과
`collectPaged`의 종료 판정 `totalResults >= 0 && start + entryCount >= totalResults`가
**첫 페이지 직후 무조건 참**이 되어, 100건만 받고 `truncated: false`로 "전 구간을 다
훑었다"고 기록했다. ④에서 고친 잘림 버그가 다른 경로로 되살아난 것.
→ 빈 문자열을 먼저 걸러 -1을 반환하도록 수정.

### (구멍) 맵 조회가 프로토타입 체인을 탄다

`ARXIV_FIELD_PREFIX[query.searchType]`에서 `searchType`이 `'toString'`/`'constructor'`
같은 값이면 **함수가 잡힌다.** truthy라서 `if (!prefix) throw` 가드를 통과하고 쿼리에
함수 소스가 박힌다. `Subscriptions.json`은 사용자가 편집할 수 있으므로 도달 가능한
경로다. 이번에 추가한 `File.SEARCH_TYPE_ALIASES`도 같은 패턴이었다.
→ 양쪽 다 `typeof x !== 'string'` 검사로 교체.

### (보강) 빈/역전 구간에 불필요한 호출

`Backfill(from, to)`에 `from >= to`를 주면 뒤집힌 범위로 arXiv를 호출했다. 원본
`queryArxiv`에는 있던 가드라 옮겼다 — 호출 없이 즉시 빈 배열 + `coveredThrough: to`.

### (보강) 커버리지 커서 누적을 max로

페이지별 `latestPublishedMs`를 덮어쓰지 않고 `Math.max`로 누적한다. ascending이라 보통은
페이지마다 커지지만, **그 정렬을 커서 정확성의 전제로 삼지 않기 위해서**다.

## 재검토에서 확인만 하고 넘어간 것

- `requestWithRetry`의 재시도 횟수/지연 배치는 정상 (3회 요청, 2회 지연, 마지막 시도 뒤
  불필요한 대기 없음). `parseRetryAfter`는 초 단위/HTTP-date 양쪽과 `0`/음수/파싱 실패를
  모두 기본 간격으로 흘린다.
- `collectPaged` 중간 페이지에서 throw가 나면 앞 페이지 결과까지 전부 버려진다. 원본도
  동일하게 동작하며(커서 미전진 후 다음 패스 재시도) 정책[1]과 일치하므로 유지.
- **`SearchRecentPaper`가 ascending이라 결과가 "오래된 것부터" 나온다.** 상한(2000건)에
  걸리면 구간의 **최신 쪽**이 빠지는데, 지금은 `lastCoverage`를 읽는 호출자가 없어
  그대로 유실된다. 4일 재스캔 창이 들어오면 자연히 회수되므로 ⑤와 함께 정리할 것.

## 아직 안 가져온 것 (우빈 파트와 함께 정해야 함)

- **⑤ 4일 재스캔 창** — 위 구조를 옮기려면 `lastCheckedAt` 전진 주체가 필요한데
  `CollectAndSave.run()`이 미구현.
- **중복 제거** — 원본 `dedupe.ts`(run 내 seen-set + 저장 여부 확인). 페이지네이션과
  4일 재스캔이 들어오면 창이 겹치므로 **반드시 필요**해진다. 지금 004에는 없다.
- **⑦ S2 API 키 배관** — 원본은 `withApiKey()`로 `x-api-key` 헤더를 붙인다
  (`semanticScholarClient.ts`). 우리는 `Secret`에서 키를 꺼낼 경로 자체가 없다(위 참고).
