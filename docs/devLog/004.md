# 8월 4일 작업 기록 (신빈 — API & SearchQuery 구현)

## 2026-08-04 확정 사항 (팀 논의로 정한 것들)

- **`searchType` 값 확정**: `keyword`(전체 검색, arXiv `all:`) / `author`(저자, `au:`) / `category`(분류, arXiv 전용 값 체계 `cs.AI` 등) 3종. UI에 임시로 있던 `domain`은 아직 `category`로 안 바뀐 상태.
- **구독 결합 규칙 확정**: API 하나당 조건 최대 3개, 전부 **AND**로 결합 (넓히는 OR이 아니라 좁히는 방향). 같은 타입 여러 개도 AND.
- **API 객체의 정체성 재정의 (우빈 제안, 논의 후 채택)**: `API`는 "외부 서비스 하나"가 아니라 **"Paper를 완성하는 하나의 방법"**. 인용수처럼 Paper에 필수인 정보를 arXiv가 못 주면, `ArxivAPI`가 반환 전에 다른 소스(S2)로 채워서 "완성된 Paper"를 내놓는다. 이 결정으로 인용수 보강을 별도 Middleware로 뺐다가 다시 API 안으로 합침 (아래 "시행착오" 참고).
- **실패 처리 정책 3단계 확정**:
  1. 수집 자체 불가(요청/파싱 실패) → `throw` — 결과를 신뢰할 수 없으므로 호출자가 실패로 판단해야 함
  2. 개별 논문 필드 누락 → 그 논문만 제외, 나머지는 정상 진행
  3. 보강(인용수 등 선택 정보) 실패 → 예외 삼키고 플래그(`citationsKnown=false`)로 남겨 다음 수집에서 재시도
  - 새 API를 추가해도 이 세 규칙을 그대로 따르면 실패 동작이 API마다 갈리지 않음.

## 진행한 작업

### `src/collect/API.ts`
- **`ArxivAPI.SearchBase()` / `SearchRecentPaper(hours)` / `Backfill(from, to)`** — 전부 스텁(`throw`)이었던 걸 실제 구현으로 교체. 셋 다 `private collect(dateFilter?)` 공통 경로를 타며 날짜 필터 유무만 다름.
- **`buildSearchQuery` / `formatTerm`** — `SearchQuery[]`를 arXiv 쿼리 문자열(`all:x AND au:y AND cat:z`)로 변환. 공백 있는 값은 구문 검색(`"따옴표"`) 처리.
- **`parseEntry`** — Atom XML `<entry>` 하나를 `Paper`로 매핑 (title/authors/abstract/sourceId/publicationDate/collectedApi/collectedQuery 등). 필수 필드(id/title/summary) 없으면 `undefined` 반환해 그 논문만 건너뜀 (실패 정책 2번).
- **`fetchAndParse`** — arXiv 호출 + XML 파싱을 묶은 함수. 실패 정책 1번(throw) 적용.
- **`enrichCitations` / `fetchCitationBatch`** — S2 인용수 보강. 논문 하나씩 호출하면 rate limit 위험이 커서, `POST /paper/batch`로 **최대 500건씩 한 번에** 조회하도록 구현 (50건 검색 시 요청 수가 50→1로 줄어듦). 실패해도 `citationsKnown=false`로 남김 (실패 정책 3번).
- **`extractArxivId`** — `".../abs/2501.12345v2"` → `"2501.12345"` (버전 접미사 제거).

### `src/collect/ApiSupport.ts` (신규 파일)
공용 실패 처리 도구 모음. 새 API를 추가할 팀원이 이 파일만 보면 규칙을 알 수 있게 문서화.
- **`requestWithRetry(param)`** — 429만 최대 3회 재시도(3초 간격), 그 외 4xx/5xx는 throw.
- **`parseXml(xmlText, source)`** — 파싱 실패(차단 페이지 등)를 "결과 0건"과 구분해 throw.
- **`hasRequiredFields(...values)`** — 필수 필드 검증.
- **`enrichQuietly(task)`** — 보강 작업 실패를 삼키는 래퍼.

### `src/collect/SearchQuery.ts`
- **`combineQueries(querys)`** 추가 — AND로 묶인 여러 조건을 `Paper.collectedQuery`용 대표 값 1개로 합성. arXiv 지식이 없는 순수 함수라 `API.ts`가 아닌 여기 배치 (신빈 담당 파일 + 002.md에서 확장 허용된 파일).

### `src/adapter/SettingTab.ts`, `src/adapter/ArxivResultModal.ts` (신규 파일)
- "arXiv API 테스트" 섹션 추가 — `CollectAndSave.run()` 완성 전에 `ArxivAPI.SearchBase()`를 단독으로 검증할 수 있는 임시 UI. 결과는 저장하지 않고 `ArxivResultModal`로 필드별 매핑 확인 + JSON 클립보드 복사만 제공.
- 저장하지 않는 이유: "흐름 제어(수집→미들웨어→저장)는 `run()`만 담당한다"는 원칙(001.md) 유지.

## 확정한 판단들 (팀원 확인 필요 시 참고)

1. **arXiv 엔드포인트는 `https://`로 고정.** `http://`는 301로 리다이렉트되는데 `requestUrl`이 이를 안정적으로 따라간다는 보장이 없어 처음부터 https 사용.
2. **S2 인용수 보강은 미들웨어가 아니라 API 안에 통합.** 원래 `run()`의 `미들웨어(forEach)` 단계로 분리하려 했으나(다이어그램상 그게 원칙에 더 맞음), 우빈이 "API=Paper를 완성하는 방법"이라는 해석을 제시해 논의 후 이쪽으로 결정. **트레이드오프**: `run()`이 아직 미구현이라 미들웨어 방식이면 지금 아무것도 검증할 수 없었는데, API 통합 방식은 `run()`과 무관하게 지금 바로 동작·검증 가능. 팀 확인 시 이 결정이 맞는지 짚어볼 것.
3. **`Paper.ts`는 건드리지 않음.** 리팩터링 과정에서 공용 헬퍼(`createCollectedPaper`)를 잠깐 `Paper.ts`에 넣었다가, 우빈 담당 파일이라는 걸 확인하고 되돌림. `Paper` 관련 공용 로직이 필요하면 `API.ts` 안에 두거나 우빈과 상의 후 옮기기로.
4. **`Middleware.ts`엔 결국 아무것도 추가 안 함.** 인용수 보강을 여기 넣었다가(`CitationEnrichMiddleware`) 3번 결정으로 빼서 다시 원상복구. `Middleware`는 여전히 인터페이스만 있는 빈 확장점.
5. **`MAX_RESULTS = 50`은 근거가 약한 임의값.** 팀 합의나 스펙에서 나온 숫자가 아니라 감으로 정함. 실제 임베딩/저장 부하나 구독당 신규 논문 수를 보고 나중에 조정 필요.
