# Decompose a Spec

Take a **rough, sprawling, or oversized** description of what should be built, clarify it with the user until they explicitly confirm it, then **split it into several right-sized specs** that can each go through `/speckit-specify` on their own.

This sits **upstream of `/speckit-specify`**. It exists because a single spec covering an entire system produces a `plan.md` nobody can execute and a `tasks.md` that never converges. Decompose first, then specify each piece.

**This skill does not write a spec.** It produces a clarified overview plus a set of scoped *spec briefs*. `/speckit-specify` turns each brief into a real `spec.md`.

## User Input

```text
$ARGUMENTS
```

Interpret the input as one of:

1. **Rough content** — a paragraph, a brain dump, a bulleted wish list, meeting notes, a draft spec, an oversized existing `spec.md`. **However rough is fine; that is the point.**
2. **A slug reference** — `slug=<name>`, `--slug <name>`, or a bare token matching an existing directory under `.specify/decompositions/`. This enters **Revision Mode** (see below).
3. **A mix** — rough content plus a slug, meaning "revise this decomposition with this new information".
4. **Empty** — ask the user what they want to decompose (interactive), or stop with a note that there is nothing to decompose (automated).

## Pre-Execution Checks

**Check for extension hooks (before decomposition)**:
- Check if `.specify/extensions.yml` exists in the project root.
- If it exists, read it and look for entries under the `hooks.before_decompose` key.
- If the YAML cannot be parsed or is invalid, skip hook checking silently and continue normally.
- Filter out hooks where `enabled` is explicitly `false`. Treat hooks without an `enabled` field as enabled by default.
- For each remaining hook, do **not** attempt to interpret or evaluate hook `condition` expressions:
  - If the hook has no `condition` field, or it is null/empty, treat the hook as executable
  - If the hook defines a non-empty `condition`, skip the hook and leave condition evaluation to the HookExecutor implementation
- When constructing slash commands from hook command names, replace dots (`.`) with hyphens (`-`). For example, `speckit.git.commit` → `/speckit-git-commit`.
- For each executable hook, output the following based on its `optional` flag:
  - **Optional hook** (`optional: true`):
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **Mandatory hook** (`optional: false`):
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding.
    ```
    After emitting the block above you MUST actually invoke the hook and wait for it to finish before continuing. Emitting the block alone does not run the hook.
- If no hooks are registered or `.specify/extensions.yml` does not exist, skip silently.

## Slug Resolution

**Ancestor path safety (do this before any filesystem lookup in this section)**: where `.specify` or `.specify/decompositions` already exist, verify each is a real directory (not a symlink) that resolves inside the project root, and refuse and report if either exists as a symlink or escapes the root — a not-yet-created directory is allowed and will be created safely later. Only then run any existence check or directory enumeration below.

Each decomposition gets its own directory under `.specify/decompositions/<slug>/`. Resolve the slug in this order:

1. **User-provided slug**: normalize it — lowercase; convert runs of whitespace/underscores to `-`; keep only `a–z`, `0–9`, and `-`; drop every other character (including `.`, `/`, `\`); collapse repeated `-`; strip leading/trailing `-`. Do not append timestamps or numbers.
2. **Interactive mode**: if no slug was provided, **ask the user** and wait. Suggest a 2–4 word kebab-case candidate derived from the content.
3. **Automated mode**: generate a concise slug (2–4 kebab-case words). If `.specify/decompositions/<slug>/` already exists and this is a *new* decomposition, append the shortest disambiguating suffix (`-2`, `-3`, …) or a short ISO date (`-20260728`).

**Reject unsafe slugs.** If the normalized slug is empty (e.g. the input was `../..`, `/`, or non-ASCII-only), refuse it: ask again (interactive) or stop with a note (automated). Never build a path from an unnormalized slug.

After resolution, set `DECOMP_SLUG` and `DECOMP_DIR = .specify/decompositions/<DECOMP_SLUG>`.

## Prerequisites

- **Path safety (before any `mkdir`, read, or write)**: resolve the project root and the real, symlink-resolved path of `DECOMP_DIR` and every artifact you touch. **Refuse and report — never follow —** if any path component is a symlink, or if the resolved path does not remain inside the project root.
- **IF EXISTS**: load `.specify/memory/constitution.md` for project principles. Any decomposition that violates a stated principle must be flagged, not silently produced.
- Ensure `DECOMP_DIR` exists, creating it (including missing parents) if necessary.

## Mode Selection

Determine the mode **before** doing any work and state it to the user:

| Condition | Mode |
|---|---|
| `DECOMP_DIR` does not exist | **New** — run Phase 1 → 4 |
| `DECOMP_DIR` exists and artifacts are unchanged since last confirmation | **Extend** — reconfirm, then apply new input from `$ARGUMENTS` |
| `DECOMP_DIR` exists and any artifact was edited by hand | **Revision** — see Revision Handling |

## Questioning Protocol

This protocol governs **every** interactive phase below. It is the core of this skill.

- **There is no question cap.** Unlike `/speckit-clarify` (max 5), this skill keeps asking **until the user explicitly confirms**. Never stop early because a quota was reached.
- **Ask exactly ONE question at a time.** Never batch, never reveal upcoming questions.
- **Always lead with your own recommendation**, so the user can accept with one word:
  - Multiple choice → `**Recommended:** Option [X] — <1–2 sentence reason>`, then a Markdown table of options (2–5, mutually exclusive), then: `You can reply with the option letter, say "yes"/"recommended" to accept, or give your own answer.`
  - Open answer → `**Suggested:** <proposal> — <brief reason>`, then: `You can accept with "yes"/"suggested", or give your own answer.`
- **Only ask questions whose answers change the decomposition.** Skip anything that belongs to `/speckit-plan` (technology choice, file layout, algorithms) or `/speckit-tasks` (ordering within one spec). If tempted by such a question, record it in `overview.md` under `## Deferred to Planning` instead of asking it.
- **Record every accepted answer immediately** to `DECOMP_DIR/decisions.md` — do not hold answers only in memory.
- **After each answer, re-evaluate**: the answer may make later queued questions unnecessary, or raise new ones. Requeue accordingly.
- **Offer to close the loop periodically.** After every 3rd accepted answer, and whenever the queue empties, ask: `이대로 확정할까요? (confirm / 계속 질문)`. Only an explicit affirmative advances the phase.
- **Honor early termination** ("stop", "그만", "이대로 진행") — but when the user stops with unresolved items, write them to `overview.md` under `## Unresolved` and say so in the report. Never silently drop them.
- **Never invent an answer.** If the user cannot decide, mark it `[NEEDS CLARIFICATION: …]` and carry it forward.

## Execution

### Phase 1 — Clarify the whole thing

Goal: turn the rough input into an overview both sides agree on. **Do not split anything yet.**

1. Restate the input in your own words — scope, apparent goal, who it is for. Show this to the user first so a misread is caught immediately.
2. Scan for ambiguity across these categories, marking each **Clear / Partial / Missing**:
   - Overall goal & definition of success
   - Explicit out-of-scope
   - Actors / users / personas
   - Major capabilities (the candidate split axis)
   - Data and entities that cross capability boundaries
   - External dependencies and integrations
   - Constraints (platform, performance, compliance, offline/online)
   - Sequencing constraints — what must exist before what
   - Terminology that must stay consistent across the split specs
3. Run the **Questioning Protocol** over every Partial/Missing category until the user confirms.
4. Write `DECOMP_DIR/overview.md` (template below).

### Phase 2 — Propose the split

Goal: agree on **how many** specs and **along which axis**.

1. Derive **2–3 candidate decompositions** from the confirmed overview. Give each a name, a rationale, and the resulting spec list. Typical axes — pick what the content actually supports, do not force one:
   - User-visible capability (each spec independently shippable)
   - Pipeline stage (each spec one transformation in a chain)
   - Architecture layer (data / logic / UI)
   - Risk isolation (uncertain parts split away from well-understood parts)
2. For each candidate, state honestly:
   - How many specs, and rough size of each
   - Whether each spec is **independently valuable** or only useful once its siblings land
   - The dependency edges between specs
   - What gets harder under this split (there is always a cost — name it)
3. **Recommend one** and explain why, then run the **Questioning Protocol** until the user confirms a final split. The user may accept a candidate, mix them, or hand you their own — treat any of these as valid and iterate.
4. Validate the confirmed split before writing:
   - Every capability in `overview.md` lands in exactly one spec — **no orphans, no duplicates**
   - No circular dependencies between specs
   - Each spec has at least one testable acceptance signal
   - Any spec that looks larger than the others is flagged for a further split (ask)

### Phase 3 — Write the artifacts

Create, under `DECOMP_DIR/`:

```
overview.md              # confirmed whole-scope spec
decisions.md             # every Q&A, append-only
handoff.md               # order, dependencies, per-file state
specs/
  01-<kebab-name>.md     # spec briefs, numbered in dependency order
  02-<kebab-name>.md
  …
```

**`overview.md`**

```markdown
# Decomposition Overview: <title>

- **Slug**: <DECOMP_SLUG>
- **Created**: <ISO 8601 date>
- **Last confirmed**: <ISO 8601 date>
- **Revision**: <integer, starts at 1>

## Goal

<What the whole thing is for, in 2–4 sentences.>

## In Scope

- …

## Out of Scope

- …

## Actors

- …

## Cross-Cutting Concerns

<Terminology, shared entities, constraints that every child spec must honor.>

## Split Axis

<The confirmed axis and why it was chosen over the alternatives.>

## Deferred to Planning

- <Questions deliberately not asked because they belong to /speckit-plan.>

## Unresolved

- [NEEDS CLARIFICATION: …]
```

**`specs/NN-<name>.md`** — a *brief*, not a finished spec:

```markdown
# Spec Brief NN: <title>

- **Parent**: <DECOMP_SLUG>
- **Depends on**: <NN of sibling specs, or "none">
- **Independently valuable**: yes | no — <one line>
- **Revision**: <integer>
- **Body-Hash**: <sha256 of everything below the `---` marker, or `unset`>

---

## Purpose

<Why this spec exists as its own unit.>

## Scope

- …

## Explicitly Not This Spec

- <Which sibling spec owns each excluded item.>

## Acceptance Signals

- <Testable statements. Seeds for the real spec — not exhaustive.>

## Open Questions

- [NEEDS CLARIFICATION: …]
```

**`handoff.md`** — the state table that makes Revision Mode possible:

```markdown
# Handoff: <DECOMP_SLUG>

Run `/speckit-specify` on each brief in the order below.

| # | Brief | Depends on | Status | Revision | Body-Hash |
|---|-------|-----------|--------|----------|-----------|
| 01 | specs/01-*.md | none | confirmed | 1 | sha256:… |

Status values: `draft` | `confirmed` | `specified` | `stale`

## Suggested Order

1. `/speckit-specify` with the contents of `specs/01-*.md`
2. …
```

Compute `Body-Hash` with `Get-FileHash` (PowerShell) or `sha256sum` (bash) over the file body after the `---` marker. If hashing is unavailable in the current environment, write `unset` and note in the report that revision detection will fall back to full re-review.

### Phase 4 — Report and hand off

Do **not** invoke `/speckit-specify` yourself. Each invocation creates a feature branch via the mandatory `before_specify` hook; firing several in a row would leave the user on an unexpected branch with interleaved work. Tell them the order and let them drive.

## Revision Handling

This is what makes the skill re-entrant. **A modified `.md` gets the same treatment as the original input: question until confirmed.**

1. Re-read every artifact under `DECOMP_DIR`.
2. For each brief, recompute `Body-Hash` and compare it to `handoff.md`. Mismatch, or `unset`, means the file was hand-edited.
3. Mark every edited brief `stale`, plus every brief that **depends on** an edited one (edits propagate downstream).
4. Show the user exactly what changed — file, and a short summary of the semantic difference, not a raw diff.
5. Run the **Questioning Protocol** over the changed material:
   - Does the edit move scope across a boundary? Then the sibling that lost or gained it must change too — ask.
   - Does the edit contradict `overview.md`? Ask which one wins, then update the loser.
   - Does the edit introduce a new capability? Ask whether it belongs here, in a sibling, or in a new brief.
   - Does the edit break a dependency edge or create a cycle? Ask how to resolve.
6. Only after explicit confirmation: increment `Revision` on every touched file, recompute hashes, set status back to `confirmed`, and update `overview.md`'s `Last confirmed`.
7. Append the full Q&A to `decisions.md` under a new `## Revision N — <date>` heading. **Never rewrite earlier decision history.**

## Guardrails

- **Writes are limited to `.specify/decompositions/<slug>/`.** Never modify source files, `specs/`, `spec.md`, or anything outside that directory. Reads may include the whole repository.
- **Never invoke `/speckit-specify`, `/speckit-plan`, or `/speckit-tasks`** — this skill only prepares input for them.
- **Never produce a split the user has not confirmed.** A proposal is not a decision.
- **Never silently drop a capability.** Every item in `overview.md` must appear in exactly one brief, or under `## Out of Scope` with a reason.
- **Never rewrite `decisions.md` history** — it is append-only, and it is the record of why the split looks the way it does.
- Do not solutionize. Technology, architecture, and file layout belong to `/speckit-plan`.
- If the input is too thin to decompose (a single sentence with no substance), say so and ask for more rather than inventing a five-way split.
- If the confirmed split yields exactly one spec, say so plainly and send the user to `/speckit-specify` directly — a one-way split is a legitimate outcome, not a failure.

## Completion Report

- Mode used (New / Extend / Revision) and the slug, on its own line: `Slug: <DECOMP_SLUG>`

- The confirmed split axis and why
- Table of produced briefs: number, title, depends-on, independently valuable, status
